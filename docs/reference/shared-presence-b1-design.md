# Phase B1 — Shared Presence Design (rev 11)

Repo: `/home/ubuntu/orca-fed-rebase` @ `feat/federation-1.4.185` (read-only). Goal: two paired humans on one runtime never collide silently — per-terminal "in use by `<name>`", visible typing, a who-is-where view, and a soft nudge when two people type at once. Owner framing: **seamless and fully integrated; no privacy from each other**. The doc carries nine owner decisions (Q1–Q9, §5) and the sliced B2 plan (§6). Five earlier claims were **wrong** and are corrected below: the scope of anonymous dispatch (gap 4), the assumption that only `terminal.multiplex` attaches a client to a PTY (gap 5), the assumption that `terminal.subscribe` has a negotiation channel it can reuse (gap 7), the assumption that every human keystroke reaches a PTY through a stream (gap 8 — neither the phone's native-chat composer nor the desktop's own remote input does), and the assumption that the host's renderer is a presence *consumer* (gap 9 — it receives nothing today). The design also fixes a clock-domain hazard on the host typing stamp (§2.1) and carries `self` on every roster surface.

## 1. What exists today

**Identity.** Every request from an authenticated socket carries `pairedDeviceId` (the revocable device id) into `RpcContext` (`src/main/runtime/runtime-rpc.ts:1713-1719`, declared `rpc/core.ts:63-79`), already load-bearing for per-device navigation (`rpc/methods/session-tabs.ts:23`, persisted at `src/shared/persisted-state-types.ts:67`). `ctx.clientId` **is the device token** (`runtime-rpc.ts:1715`) — never shippable to a peer. `ctx.clientKind` is `device.scope` (`runtime-rpc.ts:1718`, typed `'mobile' | 'runtime'` at `rpc/core.ts:77`) — a **host-observed** grant property, unlike `request.client.type`, which is client-declared and identical for the CLI and the desktop renderer alike (`z.enum(['mobile','desktop']).default('desktop')`, `rpc/methods/terminal.ts:1056`; `src/cli/handlers/terminal.ts:92`). Human-readable names live only host-side in `DeviceEntry.name` (`src/main/runtime/device-registry.ts:17-29`, `getDevice` at `:155`); **no device name crosses to any client today** — `status.get` returns the caller's own `pairedDeviceId` and nothing else (`rpc/methods/status.ts:5-18`), and enumeration exists only as Electron IPC (`src/main/ipc/mobile.ts:205,226`).

**Transport.** `remote-runtime.shared-control.v1` multiplexes control-plane JSON only. `terminal.multiplex` is excluded and keeps its own socket (`src/main/ipc/runtime-environment-transport-routing.ts:290-292`), while `runtime.clientEvents.subscribe` and `session.tabs.subscribe` ride shared-control (`:294-300`). Both are authenticated WebSockets, each with its own `connectionId` (8 random bytes per socket, `rpc/mobile-socket-wiring.ts:141`). **One desktop peer therefore holds two or more connectionIds** — the most important fact for the data model below. `runtime.clientEvents` is the only host→every-client broadcast bus (`rpc/methods/client-events.ts:15-58`, fan-out at `src/main/runtime/orca-runtime.ts:5256-5274`).

**Per-PTY registries exist and are published nowhere.** `remoteDesktopViewers` (`orca-runtime.ts:3180`, mutators `:14217-14321`), `mobileSubscribers` (`:3118-3132` — already a per-PTY mobile attach roster carrying `subscribedAt` and `lastActedAt`), `remoteTerminalViewSubscriberCounts` (`:3140`). No RPC enumerates devices.

**Correction to the input maps.** A presence event on the terminal stream needs **no new binary opcode**. `driver-changed` and `fit-override-changed` ride `emit()` on the JSON-RPC streaming reply (`terminal.ts:2726-2764`), not a binary frame; the renderer decodes them with an `if/else-if` chain with no default branch (`src/renderer/src/runtime/remote-runtime-terminal-multiplexer.ts:646-719`) over a union with an open fallback member (`:60`). Rule 2's opcode dance is unnecessary; Rule 3 gating is what binds. The cross-version harness records **binary opcodes only** in `frameSequence` (`tests/e2e/cross-version-wire/terminal-skew-journey.ts:125`), so a JSON stream event leaves `EXPECTED_JOURNEY_FRAMES` untouched.

**Honest gaps that constrain the design.**
1. No *distinguishing* label, but the plumbing exists: `createPairingOffer` is `` args.name ?? `CLI <date>` `` (`runtime-rpc.ts:702`) — a caller **can** name a device at pairing time; today every caller passes a host-minted date string (`src/main/index.ts:1904-1907`, `ipc/mobile.ts:117`, `:185`). Missing: any entry point that asks a human, and any rename-after-pairing path. `orca environment add --name` (`src/cli/specs/environment.ts:8`) names the environment **client-side only** (`KnownRuntimeEnvironment.name`, `src/shared/runtime-environments.ts:25`); the host never sees it. Q3 owns this.
2. `getOrCreatePendingDevice` reuses the first never-connected row of a scope (`device-registry.ts:105`), and `orca serve` mints exactly one offer at startup (`src/main/index.ts:1898-1908`) with no runtime re-mint RPC (`pairing.*` is only `getEndpoints`/`provisionRelay`, `rpc/methods/pairing.ts:9,19`). So **two humans handed one link get one `deviceId` and one token**. `hasOtherConnections` (`mobile-socket-wiring.ts:215-219`) compares `device.deviceToken` — "one grant, many sockets" is byte-identical to "one grant, two humans". Q1 fixes this and is a hard prerequisite for Q2.
3. No typing signal on the remote path: desktop Input (opcode 7) reaches the PTY unattributed — `clientId` is mobile-only (`terminal.ts:339`). The one desktop activity ping is `ClaimViewport`, gated on focused geometry change (`components/terminal-pane/pty-connection.ts:3939-3956`), and its `activity` is a monotonic counter, not a clock (`orca-runtime.ts:14240`).
4. **Corrected.** Anonymity is *local*, not *non-streaming*. `handleWebSocketMessage` (`runtime-rpc.ts:1609`, wired from `MobileSocketWiring.onText` at `:1311-1322`) routes **every** request from an authenticated WS/relay socket — streaming or not — through `dispatchStreaming` (`:1713`), and `dispatchStreaming` threads `connectionId`/`clientId`/`pairedDeviceId`/`clientKind`/`clientCapabilities` into non-streaming handlers too (`rpc/dispatcher.ts:167`, `:186-190`). The anonymous paths are exactly two, and both are local: the Unix-socket/named-pipe CLI (`runtime-rpc.ts:1146` → `handleMessage` `:1519` → `dispatcher.dispatch(request, { signal })`, whose options type has no identity slot, `dispatcher.ts:44`), and the Electron renderer bridge, which builds a fresh dispatcher on a hardcoded `{ id: 'desktop-ipc', authToken: 'desktop-ipc' }` envelope (`src/main/ipc/runtime.ts:52-65`). **Consequence: `terminal.list` *does* know who is asking whenever the caller is remote** — so W6 can carry `self` and can be mobile-gated, closing the one ungated surface an earlier draft had to concede.
5. **New gap — two attachment paths, not one.** `terminal.multiplex` (`terminal.ts:1644`) is the desktop/web path and refuses any non-WebSocket context (`:1648-1654`). Mobile does **not** use it: the phone subscribes with `terminal.subscribe` (`terminal.ts:2875`; caller `mobile/src/session/mobile-terminal-stream-subscribe.ts:10`), which has its own `subscribed` emits (`:2911-2916`, `:2973`, `:3445-3454`) and its own opcode-7 Input handler (`:3175-3186`). Any presence registry that watches only `terminal.multiplex` is blind to every phone — which Q5 now requires us not to be.
6. **New gap — the renderer's input takes three different routes and only one is RPC.** `writeRuntimeTerminalInput` branches on whether the PTY belongs to a remote environment (`src/renderer/src/runtime/runtime-terminal-inspection.ts:154-158`): a **local** PTY goes to `window.api.pty.write` (`:159-162`) → `ipcMain.on('pty:write')` (`src/main/ipc/pty.ts:7230`) / `ipcMain.handle('pty:writeAccepted')` (`:7241`) → `writePtyInput` (`:7181`) / `writePtyInputAccepted` (`:7203`), touching no RPC at all; a **remote** PTY with a live multiplex stream goes out as opcode 7 (`components/terminal-pane/remote-runtime-pty-transport.ts:2334`, `:1267`); and a **remote** PTY goes out as `terminal.send` whenever `sendRuntimePtyInputWithinLimit` (`:149`, reached from `:140` and `:146`) resolves a remote handle — **including while a multiplex stream is live**, which is how the desktop's own native chat writes (`components/native-chat/native-chat-runtime-send.ts:81`, `:149`, `:153`; `NativeChatComposer.tsx:346`), plus a second fallback inside the transport batcher itself (`remote-runtime-pty-transport.ts:1274`). All of them declare `DESKTOP_RUNTIME_CLIENT = { id: 'orca-desktop', type: 'desktop' }` (`runtime-terminal-inspection.ts:20`) — client-declared, and banned as a kind source per §1. Q4 turns the first route into an asset; the third is what makes gap 8 hard.
7. **New gap — `terminal.subscribe` cannot negotiate anything.** Its params carry a *separate* capabilities object from the multiplex Subscribe frame (`terminal.ts:1039-1046` vs `:1060-1068`) with no shared entries, and none of its three `subscribed` emits echoes capabilities at all — unlike the multiplex emit, which does (`:2650-2655`). The three are not interchangeable: `:2911-2916` is the no-PTY scrollback reply and **does** end immediately (`emit({ type: 'end' })` at `:2917`); `:3445-3454` is the live stream; and `:2973` is the **`mobileInputLeaseOnly` branch** (`:2940`), which registers cleanup (`:2946-2956`, its `end` at `:2953`), calls `handleMobileSubscribe` (`:2964`), emits `subscribed`, then `await streamClosed` (`:2974`) — a long-lived, viewless input lease, not a terminating reply. So the negotiate→echo→gate pattern W3(b) relies on has **no counterpart on the phone's path** and B2 must add one before any Q5 surface can be gated.
8. **New gap — the phone's chat composer is human input that reaches no stream handler.** Mobile native chat sends every message, clear, escape, image paste and diff-review note through the non-streaming `terminal.send` RPC (`mobile/src/session/mobile-native-chat-send.ts:64-72` and `:149-155`, `use-mobile-native-chat-stop.ts:96-102`, `mobile-image-attachment.ts:54-58`, `use-mobile-diff-review-send-actions.ts:83-87`). While chat covers the WebView the phone holds only a **lease-only** `terminal.subscribe` (`mobile-native-chat-terminal-stream.ts:48-52` → `terminal.ts:2940`), which registers no binary stream handler, so the opcode-7 site never runs either. The desktop reaches the same RPC by the third route of gap 6. So no stream-side stamp can be complete for human input, and without a fourth site Q5 would publish a chatting phone as attached-but-never-typing — visible to no one, held by no one.
9. **New gap — the host's own renderer is not a presence consumer.** The only main-process consumer of `runtime.onClientEvent` is the RPC method itself (`rpc/methods/client-events.ts:23`); there is **no main→renderer IPC bridge** for it. The desktop renderer subscribes to `runtime.clientEvents.subscribe` only **per remote environment** (`src/renderer/src/hooks/useIpcEvents.ts:1025-1054` → `runtime/runtime-client-events.ts:14-38`, which passes `selector: environmentId`), and per gap 6 a local PTY has no multiplex stream for W4 to ride. So in the Q4 topology — a human working at a desktop that also serves pairings — that human **publishes presence to everyone and receives none**. §2.3 adds an IPC lane for this; it is not a wire change.
10. `runtime.clientEvents` has no replay queue (`src/renderer/src/runtime/runtime-client-events.ts:14-23`), so a roster on it must be a full snapshot on every (re)subscribe. The cross-version harness covers the terminal stream only (`docs/reference/remote-wire-compatibility.md:98-101`).

## 2. Proposed design

### 2.1 Data model

New host module, **in-memory only** — the device registry is a whole-array secure rewrite per mutation (`device-registry.ts:301-305`) and is the wrong store for anything that ticks.

```
participants:   Map<connectionId, { participantId, pairedDeviceId, label, kind, connectedAt, lastInboundAt }>
attachments:    Map<ptyId, Map<subscriptionKey, { connectionId, lastInteractiveInputAt }>>
                // subscriptionKey 'host' is reserved: connectionId null, written by site (c)
grantWrites:    Map<ptyId, Map<pairedDeviceId, lastGrantWriteAt>>
participantIds: Map<pairedDeviceId, participantId>      // mint-once, process-local
```

**Identity — one participant is one device grant.** `participantId` is `randomUUID()`, minted on first sight of a `pairedDeviceId` and reused for every later connection of that grant. It is **not** the registry `deviceId`: `deviceId` is the relay binding identity (`device-registry.ts:36`, `:165`) and the on-disk key for per-device navigation (`persisted-state-types.ts:67`); broadcasting a peer's raw `deviceId` to every client is a disclosure decision B1 has no reason to make. The opaque id is stable across that peer's reconnects and extra windows and rotates on host restart. `ctx.clientId` (a token) and `params.client.id` (a fresh per-pane-mount UUID, `components/terminal-pane/remote-runtime-pty-transport.ts:356`) are both banned as keys.

*Forward constraint, now load-bearing rather than hypothetical:* **nothing may ever persist against `participantId`, and Q2's arbitration must key on `pairedDeviceId`.** Per-peer UI preferences and any write arbitration key host-side on the durable grant and project to `participantId` only at the wire boundary. A `participantId` is a session-scoped display handle, not a name.

**Two stamps, not one — provenance is in the data model, not in discipline.** `lastInteractiveInputAt` lives on an *attachment* and is written only by sites (a), (b) and (c) below: a live interactive stream, or the host's guarded renderer writers. `lastGrantWriteAt` lives in `grantWrites`, keyed by `pairedDeviceId` rather than by `subscriptionKey`, because site (d) is a bare RPC — a `terminal.send`-only writer has no subscription and therefore no `subscriptionKey` to hang a stamp on. **The `host` row is the mirror case and takes the opposite answer, not this one:** it has no `pairedDeviceId` either, so it cannot live in `grantWrites`; site (c) writes it into `attachments` under the **reserved `subscriptionKey` `'host'`** with `connectionId: null` — the same `'host'` string §2.6 uses as its grant sentinel, so both maps agree on one identifier for the local human. Keeping the host in the *interactive* map is what lets it read as **typing** rather than *writing*, and what lets it arm a hold at all (§2.6). Two derived flags follow: **`typing = now - lastInteractiveInputAt < 3000`** and **`writing = now - lastGrantWriteAt < 3000`**. `shouldHoldInputForTypingPeer` (§2.6) reads **only** `lastInteractiveInputAt`, so "site (d) never arms a hold" is a property of which map the predicate opens, not a rule an implementer must remember. The UI keeps the distinction the copy rule of §2.1 demands: interactive stamps render **"`<label>` is typing"**, grant writes render **"`<label>` is writing"** — literally true of an agent driving a human's grant, and the only wording that stays honest given the residual case below.

**Kinds.** `kind: 'runtime' | 'mobile' | 'host'`. `runtime` and `mobile` come from `device.scope` (`runtime-rpc.ts:1718`), never from a client-declared field. `host` is the single synthetic entry of Q4 below. Per Q8 there is no opt-out and no `--no-presence`: every kind is published to every client on every surface.

**Creation point and the double-count trap.** A record is created in `MobileSocketWiring.onReady` (`mobile-socket-wiring.ts:163-176`), i.e. for **any** authenticated socket, not only a terminal stream — otherwise a peer connected with no terminal open never appears, which is most of what the roster exists to show. `AuthenticatedMobileSocket` (`:36-42`) carries `connectionId`, `device.scope` and `clientCapabilities`, but `E2EEAuthenticatedDevice` is `{ deviceId, deviceToken, scope }` (`toAuthenticatedDevice`, `:60-66`) and **carries no name**, so the label is fetched at the creation point with `deviceRegistry.getDevice(socket.device.deviceId)?.name` (`device-registry.ts:155`, `DeviceEntry.name` at `:19`). The wiring type already hands the socket to the callback (`onReady?: (socket: AuthenticatedMobileSocket) => void`, `:55`, invoked at `:175`); only the current consumer discards it (`runtime-rpc.ts:1324` declares `onReady: () => { … }`), so that consumer — not the type — is what changes. Two guards make creation safe:
- *Publish only established connections.* A connection enters a payload only once it holds ≥1 live subscription. This excludes the fresh one-shot socket every remote `orca` command opens (`src/shared/remote-runtime-client.ts:235`), which registers nothing and would otherwise flash a participant in and out per command, while `terminal.multiplex` registers `terminal-multiplex:${connectionId}` (`terminal.ts:2864-2868`), `terminal.subscribe` registers `${terminal}:${clientId}` (`:2946-2956`, `:2996-3010`, `:3121-3141`) and `runtime.clientEvents.subscribe` registers its own id (`client-events.ts:30-40`) — all with the `connectionId`. The index that answers this, `subscriptionsByConnection`, is **`private`** (`orca-runtime.ts:2992`, populated by `registerSubscriptionCleanup` at `:12861-12886`, swept at `:12982`), so B2 adds one narrow read accessor — `hasEstablishedSubscription(connectionId): boolean` — on `OrcaRuntimeService`. That file is grandfathered (`config/max-lines-baseline.txt:141`); do not widen the map's visibility.
- *The `host` participant is exempt from both guards, by construction.* It has no socket and no subscription — the reserved attachment key below is neither — so it is not created in `onReady` and cannot satisfy the established-subscription test. It is instead a **static row synthesized at snapshot time** in `terminal-presence-snapshot.ts`, always present in every payload the host builds. Its `attachedTerminals` come from `resolveActiveTerminal` below and its `typing` is read from the reserved `'host'` attachment key above: the *row* is synthesized, but its activity stamp is an ordinary entry in the ordinary `attachments` map, which is why every predicate that walks that map — the Q2 gate included — sees the host with no special case. That is why a headless `orca serve` still shows `devbox (host)` with nothing attached: the row does not depend on anything connecting.
- *Aggregate by `participantId`, never by `connectionId`.* One desktop's shared-control socket and each of its terminal sockets collapse to exactly one payload entry. `attachedTerminals` is the union across that participant's connections; `connectedAt` is the minimum. This is the stated aggregation key for W4, W6, W8 and W9 alike. The one attachment whose `connectionId` is `null` — the reserved `'host'` key — skips the `connectionId → participantId` lookup and resolves directly to the `host` participant, which is the only reason that key can carry a `null` there.

**The host entry (Q4).** One synthetic participant, `participantId: 'host'`, `kind: 'host'`, absorbing the renderer bridge, local `orca`, and every other anonymous caller (gap 4) — mirroring the `{ kind: 'host' }` fallback at `rpc/workspace-creator-context.ts:8-14` and the `'in-process'` improvisation at `rpc/terminal-close-attribution.ts:41-44`.
- *Label.* **No host-published machine name exists anywhere today** — `RuntimeStatus` has none (`orca-runtime.ts:5089-5136`) and `runtimeId` is a per-process `randomUUID()` (`:2775`). The in-repo precedent, and the one to copy verbatim, is the SSH shared-workspace presence roster: `const CLIENT_NAME = hostname() || 'This device'` (`src/main/ipc/remote-workspace.ts:23`), published as a roster `clientName` (`:471-476`, typed `shared/remote-workspace-types.ts:27-32`). So the label is `` `${hostname() || 'This device'} (host)` `` — e.g. `devbox (host)`. It needs **no capability and no `status.get` change**: the host builds every presence payload itself, so the string simply rides the already-gated W4/W6/W8 payloads. The `(host)` suffix is a localization-catalog string, not a concatenated literal.
- *Typing, and it is genuinely separable.* Per gap 6 the local renderer and local CLI share no code path at any layer, and the discriminator is **not** a client-declared field: `isPtyWriteEventFromMainWindow` (`pty.ts:7173-7179`, `event.sender === mainWindow.webContents` plus destroyed-checks) gates both IPC entry points, so only the real desktop renderer's main frame reaches `writePtyInput`/`writePtyInputAccepted`, and a CLI process cannot forge an `IpcMainEvent`. Every other local writer — `orca terminal send` → `terminal.send` (`terminal.ts:1225`) → `writeTerminalAction` (`orca-runtime.ts:17537`) → `writeTerminalInputChunks` (`:17589`) → `ptyController.write` (`pty.ts:5431`) — bypasses them entirely and never touches `lastInputAtByPty` (set at `:7192` and `:7217`). **So host typing is stamped in those two functions and nowhere else**, and a scripted `orca terminal send` correctly never lights the host chip. *It is stamped into the presence registry, never into `lastInputAtByPty`* — see the clock-domain rule below. Rejected alternative, recorded: discriminating on `requestId === 'desktop-ipc'` (`ipc/runtime.ts:59`) versus the CLI's `randomUUID()` (`src/cli/runtime/transport.ts:36`) works today only by accident — `dispatch` copies `requestId: request.id` verbatim (`dispatcher.ts:91`), so any Unix-socket caller could assert it.
- *`self` is coarser than typing, deliberately — on W6 only.* On the `terminal.list` payload that feeds the CLI roster (W6), any anonymous local caller — the renderer bridge *and* a local `orca` process — sees `self: true` on the `host` row, because §2.1 already declares them one participant and no host-side fact separates them at dispatch (gap 4). Typing is finer only because the IPC guard above happens to exist on that one path. So `orca environment roster` run on the host marks the host row `self` while that row is not typing — correct on both counts, and stated here so the asymmetry is not read as a bug.
- *Attachments.* The host entry's `attachedTerminals` is the authoritative window's active terminal, read through the existing `runtime.resolveActiveTerminal(worktree)` that backs `terminal.resolveActive` (`terminal.ts:1148-1152`) — the same "what is selected and visible" lane Q7/Q9 use. On a headless `orca serve` there is no `mainWindow`, so the host entry appears with no attachments and never types. That is correct and honest, not a bug.

**Mobile (Q5) — included, with an explicitly weaker liveness contract.** Attachment needs **no new registry**, and a phone's activity splits by route exactly as §2.1 defines: terminal-screen keystrokes land at site (b) and read as *typing*, while chat sends land at site (d) and read as *writing*. `mobileSubscribers` (`orca-runtime.ts:3118-3132`) already keys per-PTY per-client with `subscribedAt`/`lastActedAt`, is cleaned on unsubscribe (`terminal.ts:3121-3141`) and on disconnect (`runtime-rpc.ts:1334-1344`), and honours a 250 ms `SOFT_LEAVE_GRACE_MS` re-subscribe absorber (`orca-runtime.ts:15354`) the roster must respect or a phone will flicker on every reconnect. What mobile *cannot* have is a bounded reap horizon, and the design says so on the wire rather than pretending:
- *There is no host-side liveness on a relay data socket.* `RemoteRuntimeServerHeartbeat` has exactly one construction site, `rpc/ws-transport.ts:83` (15 s sweep × 3 misses ⇒ ~60 s, `rpc/remote-runtime-server-heartbeat.ts:7`), and it is direct-WebSocket only. `relay-transport.ts` holds two timers and neither is liveness: an attach deadline cancelled on the first inbound frame (`:152-176`) and a close deadline armed only inside `stop()` (`:241-249`, `RELAY_SOCKET_CLOSE_TIMEOUT_MS = 5_000` at `:9`). `RELAY_CONTROL_SILENCE_LIMIT_MS = 75_000` (`relay/relay-control-silence-watchdog.ts:3`) bounds the host↔relay **control** link only, and firing it is host-wide (`relay-control-client.ts:66-69` → terminate → origin rotation), never a per-phone signal. A data socket is finalized only when the far side closes it (`relay-transport.ts:222` → `:293-306` → `mobile-socket-wiring.ts:102,209-221` → `runtime-rpc.ts:1334-1344`).
- *A host-initiated ping is inert until the phone ships.* The mobile client drops every inbound frame that is not a well-formed response (`mobile/src/transport/rpc-client.ts:514`, `mobile-relay-rpc-session.ts:212`, shape at `rpc-response-shape.ts:3-23`), so a host `ping` would be discarded with no reply. The relay session also **deliberately disables idle probes** — `idleProbeMs: null` (`mobile-relay-rpc-session.ts:141`), locked by a test named "sends no periodic traffic while an authenticated relay is idle" (`mobile-relay-rpc-session-liveness.test.ts:95`) and justified by "background phones must not hold billed relay data splices" (`mobile-endpoint-supervisor.ts:178`). The only periodic app traffic is foreground- and screen-scoped (`mobile/src/worktree/host-worktree-refresh.ts:37-48` @3 s; `use-mobile-session-tabs-reconciliation.ts:131` @2 s), so **an idle, live phone can be silent for minutes**. Mobile also never sends terminal-stream acks (it uses `terminal.subscribe`, not `terminal.multiplex`), so there is no backpressure signal either.
- *Worst case, measured against the code.* Backgrounding and app close are **explicit** disconnects — `AppState` → `setForeground(false)` → `suspendActiveRelay` (`mobile-endpoint-supervisor.ts:170-184`) → session close → socket close — so the dominant real-world case reaps promptly. Crash, force-kill and network loss are **unbounded in-repo**: the relay owns when the host-side leg closes, there is no `conn-closed` control message (`relay/relay-control-protocol.ts`), and the entry would otherwise persist until host shutdown.
- *Therefore, the deliverable contract.* B2 stamps `lastInboundAt` per connection where every inbound frame already lands (`runtime-rpc.ts:1311-1322`, `mobile-socket-wiring.ts:206`) and renders mobile rows as `attached` while fresh and `attached · last seen Nm ago` past `MOBILE_PRESENCE_STALE_MS` (start at 120 s). **Silence alone never removes a row** — that would false-reap the idle-but-live phone the code above proves is normal. Removal stays lifecycle-driven. Runtime-scope rows keep the ~60 s heartbeat bound and never show a staleness suffix, so the two contracts are visibly different in the UI rather than silently blended. A bounded mobile reap requires a mobile release (cheapest: flip `idleProbeMs: null` to a value, reusing the existing watchdog and the allowlisted `status.get`) and is explicitly **not** promised by B1.

**Staleness / TTL for the rest.** Attachment presence has no lease: it lives exactly as long as the stream. The two activity flags are the only TTL'd fields, both on a 3000 ms window over their own stamp (§2.1): `typing` over `lastInteractiveInputAt` (Q6: per-keystroke stamping) and `writing` over `lastGrantWriteAt`. Both falling edges and the emission floor are owned by the coalescer below.

**Coalescing — generalize the existing mechanism, do not hand-roll timers.** `createMobileSessionTabsNotifyCoalescer` (`src/main/runtime/mobile-session-tabs-notify-coalescer.ts:43-45`) is already a per-key trailing-edge coalescer with `schedule/cancel/flush/flushAll/dispose` (`:17-30`) and — the part a bespoke timer would omit — a **max-wait starvation cap** (`SESSION_TABS_FLUSH_MS = 50`, `SESSION_TABS_MAX_WAIT_MS = 250`, `:12-15`), built for the same shape of problem: high-frequency PTY-driven churn fanned out per client. B2 lifts the timer core into `src/main/runtime/keyed-trailing-edge-coalescer.ts` (same five-method contract, window and max-wait as constructor arguments), leaves `createMobileSessionTabsNotifyCoalescer` as a thin wrapper keeping its two constants and its existing test green, and gives presence three instances: one keyed by `ptyId` for W4, one single-key for W8 membership, one keyed by `worktreeId` for W9 (all 750 ms window / 2250 ms max-wait). (`terminal-focus-navigation-coalescer.ts` is a second precedent in that directory; it is last-write-wins routing, the wrong shape for trailing-edge fan-out.)

**Where the two stamps are written — four sites, complete for *human* input, and split by provenance.** Sites (a)–(c) write `lastInteractiveInputAt` on the attachment; site (d) writes `lastGrantWriteAt` on the grant. (a) multiplex opcode 7, **after** the empty-text guard (`terminal.ts:2161-2164`) and **before** `isTerminalInputLockedForClient` (`:2165-2167`), the Q2 gate, and the `desktopClaimTail` gate (`:2169-2181`); (b) the `terminal.subscribe` opcode-7 handler (`:3175-3186`), same ordering; (c) the two guarded host writers of Q4 — `writePtyInput` (`pty.ts:7181`) and `writePtyInputAccepted` (`:7203`), each doing `attachments.get(ptyId).set('host', { connectionId: null, lastInteractiveInputAt: Date.now() })` — stamped as the **first statement of each function, before every guard**, because both return early when a phone holds the driver (`:7183-7185`, `:7204-7206`) and two more times on ownership/provider checks (`:7186-7189`, `:7208-7213`); a stamp after those would report PTY effect, not human intent, contradicting the rule below; (d) the `terminal.send` handler (`terminal.ts:1227`, which today destructures only `{ runtime, clientId }`), covering gap 8. Site (d) carries **every** human source that is not a raw keystroke on a live stream — the phone's chat composer (gap 8), the desktop's own native chat and remote input (gap 6, third route, stream or no stream), and any human at an interactive `orca` shell — plus scripted automation, so it needs a discriminator.

**The obvious discriminator is unsound, and this is where it breaks.** `terminal.send` is remote-allowlisted (`runtime-rpc.ts:419`), so a coordinator **agent** running `orca terminal send --environment <peer>` (`src/cli/handlers/terminal.ts:86-94`) opens a one-shot authenticated WebSocket (`shared/remote-runtime-client.ts:235`) and arrives with `pairedDeviceId` set and `clientKind: 'runtime'` — identical in **every host-observed field** to a human's desktop remote send. `params.client.id` differs (`'orca-cli'` vs `'orca-desktop'`) but it is client-declared and §1 bans it as a kind source. So "`pairedDeviceId` present ⇒ human" would stamp agents as typing humans.

**Connection-level liveness does not separate them either** — checked and rejected. The desktop's remote `terminal.send` does **not** ride shared-control: `shouldUseCachedRequestConnection` routes it to a cached `RemoteRuntimeRequestConnection` (`src/main/ipc/runtime-environment-transport-routing.ts:271-273` → `runtime-environment-request-connections.ts:26-44`), a per-environment request/response socket that registers no subscriptions, exactly like the CLI's one-shot.

**What does hold is grant-level, and it is not a new rule.** §2.1 already aggregates by `pairedDeviceId` and already publishes only established participants, so: **site (d) stamps only when the sending `pairedDeviceId` already resolves to a published participant.** A desktop's grant does — the same grant holds the shared-control connection carrying `runtime.clientEvents.subscribe` (`transport-routing.ts:294-300`) — while a headless coordinator's grant holds only the one-shot and does not. This also stops (d) conjuring a roster row for someone no surface can otherwise show.

**Residual, stated plainly: no host-observed fact closes the same-machine case.** The CLI resolves the same Electron `userData` directory as the desktop (`src/cli/runtime/metadata.ts:42-56` vs `app.getPath('userData')` at `src/main/ipc/runtime-environments.ts:31`) and reads the same `orca-environments.json` (`shared/runtime-environment-store.ts:20`), so an agent shelling out **on the human's own machine shares that human's grant** and is indistinguishable from them. The rule above closes the headless-agent case — the dominant federation topology — and nothing closes the other. UI copy must therefore read a (d) stamp as *"this grant is writing to this PTY"*, which is true whether the writer is Ana or Ana's agent.

**One clock domain, and presence never reuses `lastInputAtByPty`.** Both host writers stamp that map with `performance.now()` (`pty.ts:7191-7192`, `:7216-7217`), a **monotonic process clock**, and it is read against a `performance.now()` `now` by the interactive-output heuristic (`shouldSendInteractiveOutputNow`, `:2917-2919`, called at `:3818`). The remote stamp sites have no such clock and would naturally use `Date.now()`. Mixing the two in one map and one comparison yields a `now - lastInteractiveInputAt` that is either enormous or negative — a host row that is permanently typing or never typing, deterministically, with no error. **So presence declares `Date.now()` as its single clock domain, stamps `lastInteractiveInputAt` into its own registry field, and writes nothing to `lastInputAtByPty`** — which also leaves the interactive-output heuristic's domain intact. §4.5 exercises a remote writer and a host writer against the same injected clock and asserts both TTLs expire together. Consequence, stated deliberately: a peer whose keystrokes are dropped — by a phone holding the driver lock, a failed prior claim, or a Q2 hold — still renders as "typing". Presence reports human intent, not PTY effect; going dark exactly when the peer is blocked is the worse failure.

**Disconnect cleanup — reuse existing teardown, add no new path.** `detachStream` (`terminal.ts:2041`, beside `unregisterRemoteDesktopViewer` at `:2084`) drops one attachment; `closeMultiplex` (`:2105`) drops the connection's; `terminal.unsubscribe` (`:3713-3720`) drops a `terminal.subscribe` one; `cleanupSubscriptionsForConnection` (`runtime-rpc.ts:1339`) drops the participant *connection*, and the last connection of a `participantId` drops the participant. Do **not** hang cleanup on `onClientDisconnected` — it fires only when the device has no other sockets (`runtime-rpc.ts:1342-1344`), so a two-window peer would never clear. **The reserved `'host'` attachment is the one entry no teardown above touches**, because it belongs to no stream and no connection: it dies with the PTY's whole `attachments` entry, and until then its 3000 ms TTL means a stale key reads as not-typing rather than as a phantom human. Never create a record outside a stream lifetime: the leak warning on `refreshRemoteDesktopViewer` (`orca-runtime.ts:14324-14331`) applies verbatim to one-shot `terminal.updateViewport`.

**Authority when lanes disagree.** The per-pane stream event is authoritative for its own PTY; the clientEvents roster may be one debounce interval stale, or absent while shared-control walks its reconnect ladder (`src/shared/remote-runtime-shared-control-reconnect.ts:43`). A renderer must never let a missing roster clear a chip the pane's own stream is asserting.

**W2 — optional `presence` on the `subscribed` stream event, doubly gated.** `{ participantId, label, kind, self: true }`, so a client can filter itself out of a roster. **Rule 1** in shape. **W3 — capability `terminal.presence.v1`, negotiated at two levels.** (a) Entry in `RUNTIME_CAPABILITIES` (`src/shared/protocol-version.ts:103-141`) so `status.get` advertises it and callers can probe it the way shared-control is probed (`src/main/ipc/runtime-environment-shared-control-support.ts:33-48`). **W4 — new stream JSON event `terminal-presence`.** `{ type, streamId, participants: [{ participantId, label, kind, self, typing, writing, since, stale? }], arbitration? }`, emitted beside `driver-changed` (`terminal.ts:2741-2747`, inside the `if (!isMobile)` branch at `:2726`) on subscribe and on each coalesced change, aggregated by `participantId` per §2.1. **Rule 3** — same channel, new host-published content; old clients tolerate it structurally (`remote-runtime-terminal-multiplexer.ts:646-719`, open union member at `:60`), but W3(b) gates the multiplex emit and W3(c) gates the `terminal.subscribe` mirror. `stale` is set only for `kind: 'mobile'` per §2.1. `arbitration` is Q2's soft-gate notice (§2.6). **W6 — optional `presence` on `RuntimeTerminalSummary`, opt-in by param, populated at the `terminal.list` boundary.** `presence?: { attachedCount, participants: [{ participantId, label, kind, typing, writing, self }] }` on `runtime-types.ts:451-466`. The field is **Rule 1**; the host starting to publish it is **Rule 3**, so gate *population* on a new `TerminalListParams.includePresence?: boolean` (`terminal.ts:836-847`). **Default direction, stated because the nearest precedent is the inverse:** `includeVisualLayouts` documents "Absent means 'include' so pre-flag clients keep rendering them" (`terminal.ts:844-846`). `includePresence` must be the opposite — **absent → omit the key entirely** — so a pre-presence caller's payload stays byte-identical. **And the inverse invariant, which §2.4 rests on: given `includePresence: true`, a presence-capable host emits the key on EVERY row it returns, as `presence: { attachedCount: 0, participants: [] }` when nobody is attached.** Absent key ⇒ pre-presence host; present-and-empty ⇒ nobody there. `attachedCount` counts aggregated participants, so a peer attached from two windows counts once and the CLI column can never disagree with the W4 roster beside it.

That invariant cannot be enforced inside a summary builder, because `terminal.list` has **two** of them: the renderer-graph leaf loop calls `buildTerminalSummary` (`orca-runtime.ts:15798`, declared `:30633`) and a PTY-fallback loop pushes `buildPtyTerminalSummary` rows into the *same* array (`:15815`, declared `:32558`) so that "mobile does not show a false 'No terminals' create flow" (`:15802-15804`). On a headless `orca serve` / SSH host — the deployment this feature targets — the fallback path can dominate. **So population happens once, at the boundary:** after both loops, over `listedTerminals` (`:15822`), keyed on `summary.ptyId`, which both builders always set (`:30659`, `:32568`) and which is `null` exactly when a leaf has no PTY (→ the empty object). One pass, in one place, binding on both current builders **and every future producer that feeds that array**. `terminal.show` is a different method returning a different type built from the same two builders (`:16845`/`:16862`); it gains no `includePresence` and never emits the key. `listTerminals`'s one internal caller (`:16602`) passes no option, so it stays byte-identical.

### 2.4 Roster extension (Q7 confirmed: LOCAL rows included)

**No capability probe.** `listRosterTerminals` (`src/cli/handlers/environment.ts:96-113`) makes exactly one call per peer, and `RosterProbeResponse` (`src/cli/runtime/environment-terminal-roster.ts:22-26`) has no slot for peer capabilities; a second `status.get` per peer would spend the shared probe budget (`DEFAULT_ROSTER_PROBE_TIMEOUT_MS = 10_000`, `:4`) for nothing. And a capability flag says *the host can*, not *this row was populated*; with the W6 invariant enforced per-row at the boundary, a row that lacks the key is proof enough.

So **always send `includePresence: true`**: `TerminalListParams` is a non-strict `z.object` (`terminal.ts:836-847`; the only `.strict()` schemas in that file are `:1075` and `:1082`), so an old host strips the unknown key and answers exactly as today. The capability signal is then per-terminal and free — `'presence' in terminal` — sound **only because of the W6 boundary invariant**.

`RosterTerminal` (`environment-terminal-roster.ts:16-20`) gains `presence?: string | null`: **`undefined` means the peer never published the key**, `null`/empty means nobody attached. The mapper (`handlers/environment.ts:106-110`) must preserve that distinction, and it is a **format, not a copy** — W6 ships an object while `RosterTerminal.presence` is a string, so the mapping is `'presence' in terminal ? format(terminal.presence) : undefined`, never `presence: terminal.presence ?? null` (which would lose the type and collapse "unknown" into "nobody"). `RosterRow` (`:34-44`) carries the same field. The formatter (`src/cli/environment-roster-format.ts:11-20`) renders a participant as `<label>`, `<label> (writing)` or `<label> (typing)` from the two flags, prints `-` for "nobody" and **`presence?`** for "unknown" — the existing `capability-missing` idea (`environment-terminal-roster.ts:8-12`, `:119-122`) applied per-column. Never print "nobody" for "unknown". The `local` probe is already in the list (`handlers/environment.ts:60-64`), so this runtime's own attached peers — including the `host` entry — get rows, which Q7 confirms is wanted. Update spec `notes`/`usage` (`src/cli/specs/environment.ts:24-34`; parity tests enforce spec↔handler alignment).

### 2.5 Pairing: always-mint distinct grants (Q1) and human-supplied names (Q3)

**Why `rotate: true` is not the answer.** `rotatePendingDevice` (`device-registry.ts:134-140`) filters to `retainedDevices = devices.filter(d => d.lastSeenAt !== 0 || d.scope !== scope)` — it **drops every other pending row of that scope**. Minting a named invite for Ben with `rotate` would silently kill Ana's un-scanned invite. It is a "regenerate this QR" primitive, not a multi-invite one.

**The always-mint path.** A grant can only be split per human at *offer* time, because nothing downstream can tell A's second connect from B's first (gap 2). So:
- New `DeviceRegistry.mintPendingDevice(name, scope, reach)` calling `createAndPersistDevice` unconditionally (`device-registry.ts:72-90`), leaving `getOrCreatePendingDevice` and `rotatePendingDevice` untouched so every current caller stays byte-identical.
- New optional `DeviceEntry.pendingExpiresAt?: number` (`:17-29`), written only by `mintPendingDevice` as `Date.now() + PENDING_GRANT_TTL_MS` (24 h). This is **why always-mint is safe**: the coalescing at `:94-99` exists precisely because "each call to addDevice() produces a valid auth credential" and un-scanned ones would accumulate forever. Expiry replaces coalescing as the leak control.
- A sweep dropping `lastSeenAt === 0 && pendingExpiresAt < now` rows, run inside `mintPendingDevice` and at the end of `load()` (`:206-235`). Registries written before the field exists have `pendingExpiresAt === undefined` → **never swept**, so an upgrade cannot invalidate a link already handed out.
- `createPairingOffer` gains `mint?: 'always' | 'reuse'` defaulting to `'reuse'` (`runtime-rpc.ts:662-670`, resolved at `:707-709`). Only the two named entry points below pass `'always'`.
- Budget: `device-registry.ts` is 234/300 counted, so the sweep + mint fit; if the TTL constant, the sweep and the type change exceed the margin, split the sweep into `device-registry-pending-grants.ts` rather than growing the file.

**Q3 entry points, both host-side.** `DeviceEntry.name` is set only by whoever mints the grant, so both must be on the host:
1. `orca serve --pair-name <label>` — **repeatable**, one distinct named invite per occurrence. Spec at `src/cli/specs/serve.ts:11-18` (add `pair-name`, usage, a note, an example), flag read in `src/cli/handlers/core.ts:94-133` (33 and 134 counted lines, ample), forwarded through `serveOrcaApp` options (`src/main/index.ts:1815-1850`) and consumed at `:1904-1907`, which today hardcodes `` `${mobilePairing ? 'Mobile' : 'CLI'} ${date}` ``. With ≥1 `--pair-name` the serve banner prints one pairing block per name, each `mint: 'always'`; with none, behavior is exactly as today. Rejects `--pair-name` together with `--no-pairing` the way the existing mutually-exclusive checks do (`core.ts:95-112`).
2. The desktop link flow — `mobile:getRuntimePairingUrl` (`src/main/ipc/mobile.ts:182-190`, today `` `Runtime ${date}` ``) and `mobile:getMobilePairingQR` (`:113-117`) gain an optional `name` arg passed straight through with `mint: 'always'` when present, and the renderer's pairing dialog gains a "Name this device" field. `ipc/mobile.ts` is 237/300, so the two arg additions fit.
3. **Fallback label, unchanged:** `` args.name ?? `CLI ${new Date().toLocaleDateString()}` `` (`runtime-rpc.ts:702`). Presence renders that string verbatim; it never invents a name.

**Not in scope:** rename-after-pairing (would fix already-paired devices but needs a new RPC + settings UI), and any client-supplied label on the auth frame (W7).

### 2.6 Soft arbitration (Q2)

**Behavior.** While participant A is typing on a PTY (within the 3 s typing TTL), participant B's *first* Input frame on that PTY is **held** — dropped, not queued — and B's client shows "`<label>` is typing — press again". B's next Input frame within `ARBITRATION_REPROMPT_MS` (5 s) passes through and clears the hold for that pair. Awareness plus one deliberate speed bump; no lock, no queue, no eviction, no effect on an in-flight write.

**Key: `pairedDeviceId`, never `participantId`** (§2.1's forward constraint, now enforced). A participant never gates against itself, so A's second window is never blocked. **This is exactly why Q1 is a prerequisite:** with a shared pending grant, A and B are one `pairedDeviceId`, the self-check swallows the gate, and it becomes a silent no-op that looks like it works. The `host` participant has no grant and keys on the `'host'` sentinel — the same string its reserved attachment uses (§2.1), so the predicate finds the local human in the interactive map like any other participant and **the host can hold a remote peer's keystroke**, which is the point of Q4. The converse is out of scope for B2: the host is never *held*, because its own writes enter at site (c) through `pty.ts`, which has a boolean return channel (`writePtyInput` returns `boolean | Promise<boolean>`) but no negotiated stream to carry a "press again" notice — the same reason site (d) is disarmed as a target. §2.3's local lane is where a later revision would add one.

**Shape to reuse, and shape not to.** The right precedent is `isTerminalInputLockedForClient` (`terminal.ts:284-297`): a pure host-side predicate, consulted twice — synchronously before the claim tail (`:2165`) and again inside it (`:2171`) because the tail is async and state can flip underneath. `shouldHoldInputForTypingPeer(ptyId, grantKey)` — which opens `attachments` and reads `lastInteractiveInputAt` only, never `grantWrites` — lives in `terminal-presence-arbitration.ts` and is consulted at exactly those two points in both input handlers (`:2165`/`:2171` and `:3180`/`:3184`), immediately after the `lastInteractiveInputAt` stamp so a held keystroke still reports the holder as typing. `beginMobileInputFloor` (`orca-runtime.ts:14407-14424`) is **not** the right shape and must not be reused: it is a write-serialization claim threaded through `reserveWrite`/`afterWrite` around a single send (`terminal.ts:340-356`), not a per-participant gate, and wiring arbitration into it would couple the soft nudge to the phone's hard floor.

**Telling the client.** The hold is not a silent drop. The host emits `terminal-presence` with `arbitration: { heldFor: participantId, until }` on the held stream, reusing the existing "your input did not land" notification precedent `notifyStreamWriteUnavailable` (`terminal.ts:1703`, called at `:2180`). A client that never negotiated presence on its stream receives no notice — and so, per the gate below, is never held either.

**Site (d) is disarmed in both directions — it neither holds nor arms.** It is not *held*: a held `terminal.send` could only answer with the existing not-accepted shape (`isTerminalSendRpcAccepted`, `mobile/src/session/mobile-native-chat-send.ts:78`), a bare rejection with nowhere to say why, which is worse than the collision it prevents. And it cannot *arm* holds against anyone else — not by convention but by construction: site (d) writes `lastGrantWriteAt` and `shouldHoldInputForTypingPeer` opens only the `attachments` map's `lastInteractiveInputAt` (§2.1), so there is no code path from a `terminal.send` to a hold. That split exists because §2.1 proves no host-observed fact separates a same-machine agent from the human whose grant it borrows, and an agent silently swallowing a human's keystroke would be the single worst failure this design could ship. So (d) feeds the roster as *writing*; Q2 gates exclusively at (a) and (b), where the writer is a live interactive stream. This is the honest limit of arbitration, and §4.8 asserts it rather than leaving it to review.

**Gating.** Arbitration is applied only when the *held* stream negotiated `terminal.presence.v1`. Holding input from a client that cannot render the reason would be an unexplained dropped keystroke, which is worse than a collision. Old clients therefore keep today's behavior exactly.

## 3. Non-goals for B1/B2

- **Presence is awareness plus one soft gate — not enforcement.** Q2 adds a one-shot hold with an explicit prompt; it adds **no** hard lock, no input queue, no eviction, no take-back button, and no ability for one peer to remove another. `isTerminalInputLockedForClient` stays mobile-only (`terminal.ts:284-297`), and the deliberate comment at `orca-runtime.ts:14078-14089` ("shared-control desktop viewers may still type alongside the host") stays true — a peer who presses again always gets through.
- **No change to width claiming.** `ClaimViewport` stays last-claim-wins (`orca-runtime.ts:14240-14249`); the width ping-pong two typists produce today (`pty-connection.ts:3939-3956`) becomes *visible*, not fixed.
- **No arbitration on the chat path, in either direction.** Input that arrives as `terminal.send` — the phone's composer, the desktop's own remote sends — is never held and never causes a hold, because it writes `lastGrantWriteAt` and the hold predicate reads only `lastInteractiveInputAt` (§2.1). It shows as *writing*, never as *typing*.
- **The local human arms holds but is never held.** The host's reserved attachment puts it in the interactive map, so it can hold a remote peer (Q4's purpose); nothing holds the host back, because its writes enter through `pty.ts` IPC with no negotiated stream to carry the "press again" notice (§2.6).
- **No bounded reap horizon for mobile** (§2.1) — that needs a mobile release and is not promised here.
- **Nothing persisted against `participantId`**, and no presence state persisted at all; W9's `deviceSelections` is live-only.
- No rename-after-pairing RPC, no per-device platform field, no privacy opt-out and no `--no-presence` (Q8), no `RUNTIME_PROTOCOL_VERSION` bump.

**Parallel worktrees — no lane is file-disjoint.** Every concurrent pair below shares at least one file; what makes them safe is that the shared regions are thousands of lines apart, so the merges are mechanical. Stated per pair, with the direction of the merge:
- **S1 ‖ S2** share `src/main/runtime/runtime-rpc.ts` — S1 owns `createPairingOffer` (`:662-709`), S2 owns the `onReady` consumer (`:1324`). ~600 lines apart, different methods. **S2 rebases onto S1**, because S1 is the shorter slice and the prerequisite for S6.
- **S4 ‖ S5** share `src/main/runtime/orca-runtime.ts` — S4 owns the `terminal.list` boundary pass (`:15822`), S5 owns the clientEvents fan-out and snapshot (`:5177-5274`). ~10 000 lines apart. They also both extend `src/shared/runtime-types.ts` in separate type declarations (`:451-466` vs `:341-353`), and — the one genuine overlap — both add a projection to the **same new file**, `terminal-presence-snapshot.ts`, created by S2. **S5 rebases onto S4** in all three cases: S4 is the smaller diff, S5 already carries the two preparatory extractions, and the snapshot file is the only place a real conflict can arise, so it should be resolved once, in S5's direction.
- **S6 ‖ S8** are disjoint **only because S5 is required to land the complete state shape**. Both write `lib/pane-manager/terminal-presence-state.ts`: S6's `arbitration` notice (§2.6) arrives on the same W4 payload the transport writer already forwards, and S8 pushes participants into the same map. So **S5 owns that module's shape** and must declare the `arbitration` slot (and `writing`) when it creates it, unused until S6 fills it. Given that, S6 edits `rpc/methods/terminal.ts` plus chip copy and S8 edits `src/main/ipc/` + preload + `useIpcEvents.ts`, and the pair is genuinely disjoint. Without it they collide on one file and must serialize.
- **Strictly sequential:** S3 before S6 (both edit the same two opcode-7 handlers in `rpc/methods/terminal.ts`); S2 before S3 (S3's gate reads the `supportsPresence` S2 introduces on both handlers); S5 before S7 **and** before S8 (S7 edits `rpc/methods/client-events.ts` and `terminal-presence-snapshot.ts`, both of which S5 writes; S8 consumes the renderer state lane S5 creates); S7 after S8 or vice versa is free, since S7 touches no `src/main/ipc/` file.

Recommended lanes: `[S1 ‖ S2] → S3 → [S4 ‖ S5] → [S6 ‖ S8] → S7`.
