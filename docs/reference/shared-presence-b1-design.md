# Phase B1 — Shared Presence Design (rev 5)

Repo: `/home/ubuntu/orca-fed-rebase` @ `feat/federation-1.4.185` (read-only). Goal: two paired humans on one runtime never collide silently — per-terminal "in use by <device>", visible typing, a who-is-where view.

## 1. What exists today

**Identity.** Every authenticated *streaming* socket carries `pairedDeviceId` (the revocable device id) into `RpcContext` (`src/main/runtime/runtime-rpc.ts:1713-1719`, declared `rpc/core.ts:64-79`), already load-bearing for per-device navigation (`rpc/methods/session-tabs.ts:43`, persisted at `src/shared/persisted-state-types.ts:67`). `ctx.clientId` **is the device token** (`runtime-rpc.ts:1715`) — never shippable to a peer. `ctx.clientKind` is `device.scope` (`runtime-rpc.ts:1718`, typed `'mobile' | 'runtime'` at `rpc/core.ts:77`) — a **host-observed** grant property, unlike `request.client.type`, which is client-declared (`rpc/methods/terminal.ts:2413`). Human-readable names live only host-side in `DeviceEntry.name` (`src/main/runtime/device-registry.ts:17-29`, `getDevice` at `:155`); **no device name crosses to any client today** — `status.get` returns the caller's own `pairedDeviceId` and nothing else (`rpc/methods/status.ts:7-16`), and enumeration exists only as Electron IPC (`src/main/ipc/mobile.ts:205,226`).

**Transport.** `remote-runtime.shared-control.v1` multiplexes control-plane JSON only. `terminal.multiplex` is explicitly excluded and keeps its own socket (`src/main/ipc/runtime-environment-transport-routing.ts:290-292`), while `runtime.clientEvents.subscribe` rides shared-control (`:296`). Both are authenticated WebSockets, each with its own `connectionId` (8 random bytes per socket, `rpc/mobile-socket-wiring.ts:141`). **One desktop peer therefore holds two or more connectionIds** — the most important fact for the data model below. `runtime.clientEvents` is the only host→every-client broadcast bus (`rpc/methods/client-events.ts:16-58`, fan-out at `src/main/runtime/orca-runtime.ts:5256-5274`).

**Per-PTY registries exist and are published nowhere.** `remoteDesktopViewers` (`orca-runtime.ts:3180`, mutators `:14225-14321`), `mobileSubscribers` (`:3118`), `remoteTerminalViewSubscriberCounts` (`:3140`). No RPC enumerates devices.

**Correction to the input maps.** A presence event on the terminal stream needs **no new binary opcode**. `driver-changed` and `fit-override-changed` ride `emit()` on the JSON-RPC streaming reply (`terminal.ts:2726-2764`), not a binary frame; the renderer decodes them with an `if/else-if` chain with no default branch (`src/renderer/src/runtime/remote-runtime-terminal-multiplexer.ts:646-719`) over a union with an open fallback member (`:60`). Rule 2's opcode dance is unnecessary; Rule 3 gating is what binds. The cross-version harness records **binary opcodes only** in `frameSequence` (`tests/e2e/cross-version-wire/terminal-skew-journey.ts:125`), so a JSON stream event leaves `EXPECTED_JOURNEY_FRAMES` untouched.

**Honest gaps that constrain the design.**
1. No *distinguishing* label, but the plumbing exists: `createPairingOffer` is `args.name ?? \`CLI <date>\`` (`runtime-rpc.ts:702`) — a caller **can** name a device at pairing time; today every caller passes a host-minted date string (`src/main/index.ts:1904-1907`, `ipc/mobile.ts:117`, `:185`). Missing: any rename-after-pairing path, and any entry point that asks a human.
2. `getOrCreatePendingDevice` reuses the first never-connected row of a scope (`device-registry.ts:105`), so **two humans can be handed one `deviceId` and one token**. Nothing downstream separates them: `hasOtherConnections` (`mobile-socket-wiring.ts:213-218`) compares `device.deviceToken` — "one grant, many sockets", byte-identical to "one grant, two humans". §2.1 accepts the collapse; Q1 must precede B2.
3. No typing signal: desktop Input (opcode 7) reaches the PTY unattributed — `clientId` is mobile-only (`terminal.ts:339`). The one desktop activity ping is `ClaimViewport`, gated on focused geometry change (`components/terminal-pane/pty-connection.ts:3939-3956`), and its `activity` is a monotonic counter, not a clock (`orca-runtime.ts:14240`).
4. **Only streaming RPCs carry identity at all.** `dispatch()` is declared `async dispatch(request, options?: { signal?: AbortSignal })` (`rpc/dispatcher.ts:44`) — its options type has no slot for `clientId`/`pairedDeviceId`/`clientKind`, so **every non-streaming method is anonymous, remote calls included**; only `dispatchStreaming` threads identity (`:136`, `:186-190`, `:248-252`). This is not a local/Unix-socket quirk. Two consequences carried through below: presence for a *connection* can only ever be established on a streaming path, and `terminal.list` — where W6 is populated — **cannot know who is asking**, so W6 carries no `self` flag and does no per-caller filtering.
5. `runtime.clientEvents` has no replay queue (`src/renderer/src/runtime/runtime-client-events.ts:16-22`), so a roster on it must be a full snapshot on every (re)subscribe. The cross-version harness covers the terminal stream only (`docs/reference/remote-wire-compatibility.md:98-101`).

## 2. Proposed design

### 2.1 Data model

New host module, **in-memory only** — the device registry is a whole-array secure rewrite per mutation (`device-registry.ts:301-305`) and is the wrong store for anything that ticks.

```
participants:   Map<connectionId, { participantId, pairedDeviceId, label, clientKind, connectedAt }>
attachments:    Map<ptyId, Map<subscriptionKey, { connectionId, lastInputAt }>>
participantIds: Map<pairedDeviceId, participantId>      // mint-once, process-local
```

**Identity — one participant is one device grant.** `participantId` is `randomUUID()`, minted on first sight of a `pairedDeviceId` and reused for every later connection of that grant. It is **not** the registry `deviceId`: `deviceId` is the relay binding identity (`device-registry.ts:36`, `:165`) and the on-disk key for per-device navigation (`persisted-state-types.ts:67`); broadcasting a peer's raw `deviceId` to every client is a disclosure decision B1 has no reason to make. The opaque id is stable across that peer's reconnects and extra windows and rotates on host restart. `ctx.clientId` (a token) and `params.client.id` (a fresh per-pane-mount UUID, `components/terminal-pane/remote-runtime-pty-transport.ts:356`) are both banned as keys.

*Forward constraint created by that rotation — recorded now because Q2 would inherit it silently:* **nothing may ever persist against `participantId`.** Per-peer UI preferences, a future mute/hide, and any B2 write arbitration must key host-side on `pairedDeviceId` (the durable grant) and project to `participantId` only at the wire boundary. A `participantId` is a session-scoped display handle, not a name.

*Consequence, stated rather than papered over:* two humans sharing one pending grant (gap 2) are **one participant with one label**, and B1 makes no attempt to split them. No socket-level fact distinguishes them, so a per-participant suffix would be byte-identical for both and disambiguate nothing. The fix is at pairing time — Q1.

**Creation point and the double-count trap.** A record is created in `MobileSocketWiring.onReady` (`mobile-socket-wiring.ts:163-176`), i.e. for **any** authenticated socket, not only `terminal.multiplex` — otherwise a peer connected with no terminal open never appears, which is most of what Surface 3 exists to show. `AuthenticatedMobileSocket` (`:36-42`) carries `connectionId`, `device.scope` and `clientCapabilities`, so the runtime-scope filter can be applied right there — but `E2EEAuthenticatedDevice` is `{ deviceId, deviceToken, scope }` (`toAuthenticatedDevice`, `:60-66`) and **carries no name**, so the label must be fetched at the creation point with `deviceRegistry.getDevice(socket.device.deviceId)?.name` (`device-registry.ts:155`, `DeviceEntry.name` at `:19`). The wiring type already hands the socket to the callback (`onReady?: (socket: AuthenticatedMobileSocket) => void`, `:55`, invoked at `:175`); only the current consumer discards it (`runtime-rpc.ts:1324` declares `onReady: () => { … }`), so that consumer — not the type — is what changes. Two guards make creation safe:
- *Publish only established connections.* A connection enters a payload only once it holds ≥1 live subscription. This excludes the fresh one-shot socket every remote `orca` command opens (`src/shared/remote-runtime-client.ts:235`), which registers nothing and would otherwise flash a participant in and out per command, while `terminal.multiplex` registers `terminal-multiplex:${connectionId}` (`terminal.ts:2864-2868`) and `runtime.clientEvents.subscribe` registers its own id (`client-events.ts:32-40`) — both with the `connectionId`. The index that answers this, `subscriptionsByConnection`, is **`private`** (`orca-runtime.ts:2992`, populated by `registerSubscriptionCleanup` at `:12861-12880`, swept at `:12981`), so B2 adds one narrow read accessor — `hasEstablishedSubscription(connectionId): boolean` — on `OrcaRuntimeService`. That file is grandfathered (`config/max-lines-baseline.txt:141`), so the line budget is not an obstacle; do not widen the map's visibility.
- *Aggregate by `participantId`, never by `connectionId`.* Because `participantId` is per-`pairedDeviceId`, one desktop's shared-control socket and each of its multiplex sockets collapse to exactly one payload entry. `attachedTerminals` is the union across that participant's connections; `connectedAt` is the minimum. This is the stated aggregation key for W4, W6 and W8 alike.

**Scope — runtime-scope participants only in B1** (`clientKind === 'runtime'`, i.e. `device.scope`). Rationale: the staleness bound below is a `WebSocketTransport` property that does not hold for relay, and relay is mobile-only (`src/shared/mobile-relay-pairing-offer.ts:83-91`); mobile contention already has a finished surface (`isTerminalInputLockedForClient`, `terminal.ts:284-297`, plus `MobileDriverOverlay`). Because the filter reads the grant's scope rather than a client-declared field, it is also the load-bearing suppression for mobile everywhere below. Q5 revisits it.

**Anonymous callers** (renderer, local `orca`, and per gap 4 *any* non-streaming RPC) collapse to one synthetic `host` participant, mirroring the `context.pairedDeviceId ?? 'in-process'` improvisation at `session-tab-close-methods.ts:48`. **One writer:** the host publishes presence; no client asserts it. Remote panes already have two writers for agent status and needed a fence (`components/terminal-pane/renderer-owned-agent-status-registry.ts:1`).

**Staleness / TTL.** Attachment presence has no lease: it lives exactly as long as the stream, and dead sockets are reaped by `RemoteRuntimeServerHeartbeat` — a 15 s sweep with a 3-consecutive-miss rule that `ws-transport.ts:24` documents as bounding a half-open to **~60 s** (`rpc/remote-runtime-server-heartbeat.ts:7`, constructed at `ws-transport.ts:83`). **That bound is transport-specific.** The heartbeat has exactly one construction site — `ws-transport.ts:83` — and there is none anywhere in `src/main/runtime/relay/` (the only hit is the `onConnectionClosed` wiring at `relay-control-origin.ts:55`). A relay data socket is finalized only when the relay cell says so (`rpc/relay-transport.ts:167`, `:293-305` → `mobile-socket-wiring.ts:102` → `handleClose` → `runtime-rpc.ts:1339`), so cleanup is *identical* but the detection horizon is set by a service outside this repo; `RELAY_CONTROL_SILENCE_LIMIT_MS = 75_000` (`relay/relay-control-silence-watchdog.ts:3`) bounds the host↔relay **control** link, not a per-client data connection. Hence the runtime-scope-only rule: the ~60 s figure printed in UI copy is then true of every participant B1 shows. Typing is the only TTL'd field: `typing = now - lastInputAt < 3000 ms`, with the falling edge and the emission floor both owned by the coalescer below.

**Coalescing — generalize the existing mechanism, do not hand-roll timers.** `createMobileSessionTabsNotifyCoalescer` (`src/main/runtime/mobile-session-tabs-notify-coalescer.ts:43-45`) is already a per-key trailing-edge coalescer with `schedule/cancel/flush/flushAll/dispose` (`:17-30`) and — the part a bespoke timer would omit — a **max-wait starvation cap** (`SESSION_TABS_FLUSH_MS = 50`, `SESSION_TABS_MAX_WAIT_MS = 250`, `:12-15`, enforced at `:70-90`), built for the same shape of problem: high-frequency PTY-driven churn fanned out per client. B2 therefore lifts the timer core into `src/main/runtime/keyed-trailing-edge-coalescer.ts` (same five-method contract, flush window and max-wait as constructor arguments), leaves `createMobileSessionTabsNotifyCoalescer` as a thin wrapper that keeps its two constants and its existing test green, and gives presence two instances: one keyed by `ptyId` for W4 (750 ms window, 2250 ms max-wait) and one single-key instance for W8 membership (750 ms window, 2250 ms max-wait). Sustained typing then has the *same* starvation profile as the established path instead of an unbounded one. (`terminal-focus-navigation-coalescer.ts` is a second, latest-wins precedent in that directory; it is the wrong shape here because presence needs trailing-edge fan-out, not last-write-wins routing.)

**Where `lastInputAt` is stamped — decided.** In the opcode-7 handler, **after** the empty-text guard (`terminal.ts:2161-2164`) and **before** `isTerminalInputLockedForClient` (`:2165-2167`) and the `desktopClaimTail` gate (`:2169-2181`). Consequence, stated deliberately: a peer whose keystrokes are dropped — by a phone holding the driver lock, or a failed prior claim — still renders as "typing". Presence reports human intent, not PTY effect; going dark exactly when the peer is blocked is the worse failure. B2 test 5 asserts this ordering.

**Disconnect cleanup — reuse existing teardown, add no new path.** `detachStream` (`terminal.ts:2041`, beside `unregisterRemoteDesktopViewer` at `:2084`) drops one attachment; `closeMultiplex` (`:2105`) drops the connection's; `cleanupSubscriptionsForConnection` (`runtime-rpc.ts:1339`) drops the participant *connection*, and the last connection of a `participantId` drops the participant. Do **not** hang cleanup on `onClientDisconnected` — it fires only when the device has no other sockets (`runtime-rpc.ts:1342-1344`), so a two-window peer would never clear. Never create a record outside a stream lifetime: the leak warning on `refreshRemoteDesktopViewer` (`orca-runtime.ts:14324-14331`) applies verbatim to one-shot `terminal.updateViewport`.

**Authority when lanes disagree.** The per-pane multiplex event is authoritative for its own PTY; the clientEvents roster may be one debounce interval stale, or absent while shared-control walks its reconnect ladder (`src/shared/remote-runtime-shared-control-reconnect.ts:43`). A renderer must never let a missing roster clear a chip the pane's own stream is asserting.

**Max-lines budget (binding on the module split).** Counted-line limits are 300 `.ts` / 400 `.tsx` / 800 tests, with `skipBlankLines`/`skipComments` (`.oxlintrc.json:141-160`); the ratchet fails CI on any **new** bypass (`config/scripts/check-max-lines-ratchet.mjs:7-14`) and `AGENTS.md:16` forbids a `max-lines` disable. Grandfathered and free to grow: `orca-runtime.ts`, `terminal.ts`, `TerminalPane.tsx`, `remote-runtime-terminal-multiplexer.ts`, `pty-connection.ts`, `remote-runtime-pty-transport.ts` (`config/max-lines-baseline.txt:141,149,247,275,252,256`). Split new host code as `terminal-presence-registry.ts` (maps, mutators, cleanup) + `terminal-presence-snapshot.ts` (labels, payload bounding). CLI files touched have headroom (`handlers/environment.ts` ≈126 counted, `environment-terminal-roster.ts` ≈137, `environment-roster-format.ts` 27). **`SortableTab.tsx` does not**: exactly 399 counted lines against the 400 `.tsx` limit (`.oxlintrc.json:147`), and it is **not** in the baseline, so *any* addition fails `check:max-lines-ratchet` under `pnpm lint`. B2 must land a preparatory extraction first — but **rename state only**: `SortableTab.tsx:129-203` is two responsibilities, rename (`isEditing` `:131`, `renameValue`/`renameFocusFrameRef` `:135-136`, `committedOrCancelledRef` `:138`, `handleRenameOpen`/`commitRename`/`cancelRename`/`setRenameInputElement` `:140-176`, the `renamingTabId` shortcut effect `:178-185`) *and* context-menu state (`menuOpen`/`menuPoint` `:129-130`, the `CLOSE_ALL_CONTEXT_MENUS` effect `:187-191`, the window-blur dismiss `:193-201`), and bundling both under one hook named for rename is exactly the mismatch `AGENTS.md`'s naming section forbids. Extract the rename set only — **43 counted lines**, ample for the badge — into `components/tab-bar/use-sortable-tab-rename.ts`; leave the menu state in place, where `SortableTabContextMenu.tsx` is already its component home, and let a menu extraction be its own change if one is ever needed. `SortableTab.rename-shortcut.test.tsx` covers the moved `renamingTabId` path and must stay green across the extraction (§4).

### 2.2 Wire changes, one by one

**W1 — thread `pairedDeviceId` into the multiplex handler.** `terminal.ts:1646-1650` destructures only `runtime, connectionId, sendBinary, registerBinaryStreamHandler, signal`; add `pairedDeviceId` and `clientKind` and store the resolved participant on the stream record (`:2506-2525`). *Not a wire change* — host-local, no gating. Prerequisite for W2/W4.

**W2 — optional `presence` on the `subscribed` stream event, doubly gated.** `{ participantId, label, self: true }`, so a client can filter itself out of a roster. **Rule 1** in shape. Two gates, and both matter because the `subscribed` emit (`terminal.ts:2642-2659`) sits **84 lines above** the `if (!isMobile)` branch at `:2726` and therefore fires on mobile streams too — there is no structural suppression here to lean on:
- *Negotiated:* only when `stream.supportsPresence`, riding the same conditional as the negotiated capability echo (`:2649-2655`).
- *Host-observed:* only when the stream's `connectionId` resolves to a **tracked runtime-scope participant** (§2.1). If it does not — a mobile stream, a non-runtime grant, or any connection with no participant record — **the `presence` key is omitted entirely**, not emitted as a placeholder. A placeholder would put a `participantId` on the wire that the W4 and W8 rosters can never corroborate, and would produce a self-chip with nothing behind it. Omission is also the same absent-means-nothing convention W6 uses.

Because the second gate reads `device.scope` (`runtime-rpc.ts:1718`) rather than the client-declared `request.client.type` (`terminal.ts:2413`), a future mobile build that echoed an unknown `capabilities` key still gets no label. Rev 2 left W2 ungated entirely; that was wrong for no benefit — every roster surface is gated, `label` is `DeviceEntry.name` which today never crosses to any client at all (§1), and gating makes **W3(b) the single negotiation gate for every presence byte a client will render**. That wording is deliberate and narrower than rev 4's: W8 is a broadcast with no negotiation at all, so its bytes do reach old desktop subscribers (see the matrix).

**W3 — capability `terminal.presence.v1`, negotiated at two levels.** (a) Entry in `RUNTIME_CAPABILITIES` (`src/shared/protocol-version.ts:103-140`) so `status.get` advertises it and callers can probe it the way shared-control is probed (`src/main/ipc/runtime-environment-shared-control-support.ts:33-48`). (b) Per-stream: the client advertises `capabilities.presence: 1` in the Subscribe frame (schema `terminal.ts:1060-1068` is `z.literal(1).optional()`, unknown keys stripped by the non-strict object); the host records `supportsPresence` (`:2519-2522` pattern), echoes `capabilities: { presence: 1 }` on `subscribed` only when negotiated (`:2649-2655`), and emits presence on that stream only when `stream.supportsPresence` (`:2184` pattern). Rule 2 discipline without a new opcode. **The client's advertisement is unconditional** — hardcoded into the Subscribe capabilities exactly as `outputPause` is (`remote-runtime-terminal-multiplexer.ts:519-525`), never gated on a W3(a) probe. Gating it on `status.get` would make the same-version cross-version case negotiate nothing and pass vacuously, the failure the harness's own oracle comment warns about (`cross-version-terminal-wire.unit.test.ts:57-59`). `RUNTIME_PROTOCOL_VERSION` stays 3 (`protocol-version.ts:12-18`). *Coupling:* `status.get` filters three entries conditionally today (`orca-runtime.ts:5099-5107`). If the Q8 `--no-presence` opt-out ships, `terminal.presence.v1` joins that filter and every surface follows automatically.

**W4 — new multiplex JSON stream event `terminal-presence`.** `{ type, streamId, participants: [{ participantId, label, kind, typing, since }] }`, emitted beside `driver-changed` (`terminal.ts:2741-2747`, inside the `if (!isMobile)` branch at `:2726`) on subscribe and on each coalesced change, aggregated by `participantId` per §2.1. **Rule 3** — same channel, new host-published content. Old clients tolerate it structurally (`remote-runtime-terminal-multiplexer.ts:646-719`, open union member at `:60`), but the rule binds, so W3(b) gates it. W4 is the **only** presence emit that is structurally suppressed for mobile. Deliberately not opcode 18 — opcode numbers are permanent (`src/shared/terminal-stream-protocol.ts:25-33`).

**W5 — do NOT extend `RuntimeTerminalDriverState`.** A `peer-desktop` variant (`src/shared/runtime-types.ts:57-62`) would be Rule 3 on `driver-changed` and would silently re-target `isTerminalInputLockedForClient` (`terminal.ts:284-297`) and the mobile overlay gate — turning awareness into enforcement. Listed as a non-change so review sees it was considered.

**W6 — optional `presence` on `RuntimeTerminalSummary`, opt-in by param, populated at the `terminal.list` boundary.** `presence?: { attachedCount, participants: [{ participantId, label, typing }] }` on `runtime-types.ts:451-466` (no `self` flag — per gap 4 the handler has no caller identity). The field is **Rule 1**; the host starting to publish it is **Rule 3**, so gate *population* on a new `TerminalListParams.includePresence?: boolean` (`terminal.ts:836-847`, threaded from the handler at `:1138-1145`). **Default direction, stated because the nearest precedent is the inverse:** `includeVisualLayouts` documents "Absent means 'include' so pre-flag clients keep rendering them" (`terminal.ts:844-846`). `includePresence` must be the opposite — **absent → omit the key entirely** — so a pre-presence caller's payload stays byte-identical.

**And the inverse invariant, which §2.4 rests on: given `includePresence: true`, a presence-capable host emits the key on EVERY row it returns, as `presence: { attachedCount: 0, participants: [] }` when nobody is attached.** Absent key ⇒ pre-presence host; present-and-empty ⇒ nobody there. **`attachedCount` counts aggregated participants, not connections** — the same `participantId` key §2.1 uses everywhere else — so a peer attached to one PTY from two windows counts once, and the CLI column can never disagree with the W4 roster it sits beside.

That invariant cannot be enforced inside a summary builder, because `terminal.list` has **two** of them: the renderer-graph leaf loop calls `buildTerminalSummary` (`orca-runtime.ts:15798`, declared `:30633`) and a PTY-fallback loop pushes `buildPtyTerminalSummary` rows into the *same* array (`:15815`, declared `:32558`) so that "mobile does not show a false 'No terminals' create flow" (`:15802-15804`). On a headless `orca serve` / SSH host — the deployment this feature targets — the fallback path can dominate. Threading `includePresence` through both builders would leave the invariant one future builder away from breaking. **So population happens once, at the boundary:** after both loops, over `listedTerminals` (`orca-runtime.ts:15822`), keyed on `summary.ptyId`, which both builders always set (`:30659`, `:32568`) and which is `null` exactly when a leaf has no PTY (→ the empty object). One pass over ≤`limit` rows, in one place, binding on both current builders **and every future producer that feeds that array** — which is the form the invariant has to take to be worth relying on.

`terminal.show` is a different method returning a different type (`RuntimeTerminalShow`, built from the same two builders at `orca-runtime.ts:16845`/`:16862`); it gains no `includePresence` and never emits the key, and no consumer infers capability from it. `listTerminals`'s one internal caller (`:16602`) passes no option, so it too stays byte-identical.

**W7 — explicitly no change to** the `e2ee_auth` frames (v2 asserts an exact key set, `rpc/mobile-e2ee-auth-validation.ts:13-26`), `PairingOffer`, or `session.tabs`. Publishing per-device active tab from `ClientSessionTabSelectionStore` (`src/main/runtime/client-session-tab-selection.ts:78-131`) would be Rule 3 on a channel the harness does not cover (`remote-wire-compatibility.md:98-101`) — deferred, Q9.

**W8 — new `RuntimeClientEvent` type `terminalPresence`** for the runtime-wide roster (`src/shared/runtime-client-events.ts:11`). **Rule 1** by the protocol-version comment ("adding new ignorable event types" does not bump, `protocol-version.ts:12-18`); the renderer allowlist drops unknown types silently (`src/renderer/src/runtime/runtime-client-events.ts:83-96`).
- *Cadence:* membership only — participant join/leave, attach/detach — through the single-key coalescer instance of §2.1. **Typing edges never ride this bus**; they are per-PTY and belong to W4 alone.
- *Payload:* `{ type, seq, participants: [{ participantId, label, kind, attachedTerminals: [handle] }], truncated? }`, one entry per `participantId` (§2.1 aggregation), capped at 32 participants and 64 handles each, `truncated: true` past that.
- *Mobile filter, applied in TWO places.* `runtime.clientEvents.subscribe` already carries `{ consumesTerminalSideEffects: clientKind !== 'mobile' }` with the comment "mobile discards terminalSideEffects; excluding it stops the per-OSC batch frames from crossing the relay" (`client-events.ts:19-28`). Add a sibling `consumesPresence` to `onClientEvent` (`orca-runtime.ts:5177-5194`) with the matching branch in `emitClientEvent` (`:5256-5274`) — **but that branch covers live events only.** The subscribe-time snapshot loops call the streaming reply's `emit()` directly (`client-events.ts:42-49`) and never enter `emitClientEvent`, so a listener-set filter cannot reach them; left alone, every mobile (re)subscribe would ship the largest presence payload B1 produces — desktop labels and terminal handles — straight across the relay. So the handler computes `const consumesPresence = clientKind !== 'mobile'` **once** and uses it for both the `onClientEvent` option and as the guard on the presence snapshot loop.
- *Snapshot on subscribe:* add `getTerminalPresenceClientEventSnapshot()` beside `getTerminalSleepClientEventSnapshot()` (`orca-runtime.ts:5200`), emitted listener-first inside that guard (`client-events.ts:42-49`), because events emitted while the transport was down are lost, not queued.

### 2.3 Renderer UI (paths under `src/renderer/src/`)

- *State lane:* `lib/pane-manager/terminal-presence-state.ts`, a sibling to `lib/pane-manager/mobile-driver-state.ts:16` — module-level `Map<ptyId, participants>` outside Zustand, re-rendered via the existing tick counter (`components/terminal-pane/use-mobile-overlay-ticks.ts:140`), keeping presence out of the store fanout budget (`docs/reference/renderer-agent-status-performance.md`).
- *Writer:* `components/terminal-pane/remote-runtime-pty-transport.ts` gains `onPresenceChanged → setPresenceForPty`, mirroring `onDriverChanged → setDriverForPty` (`:1862`). That file is grandfathered (`max-lines-baseline.txt:256`), as is `pty-connection.ts` (`:252`). The W8 roster writes a *separate* runtime-wide map.

### 2.4 Roster extension

**No capability probe.** `listRosterTerminals` (`src/cli/handlers/environment.ts:96-113`) makes exactly one call per peer, and `RosterProbeResponse` (`src/cli/runtime/environment-terminal-roster.ts:22-26`) has no slot for peer capabilities; a second `status.get` per peer would spend the shared probe budget (`DEFAULT_ROSTER_PROBE_TIMEOUT_MS = 10_000`, `:4`) for nothing. A status-based probe would also be plumbing, not a freebie: the compat gate's preflight `status.get` (`src/cli/runtime/remote-runtime-compat-gate.ts:44-62`) consumes the result for a version verdict and discards `capabilities` (`noteVerifiedStatus`, `:66-79`). And it would not even fix the right problem — a capability flag says *the host can*, not *this row was populated*; with the W6 invariant enforced per-row at the boundary, a row that lacks the key is proof enough.

So **always send `includePresence: true`**: `TerminalListParams` is a non-strict `z.object` (`terminal.ts:836-847`; the only `.strict()` schemas in that file are `:1075` and `:1082`, and `TerminalHandle` at `:828` is non-strict), so an old host strips the unknown key and answers exactly as today. The capability signal is then per-terminal and free — `'presence' in terminal` — sound **only because of the W6 boundary invariant**: a capable host emits the key on every returned row, fallback rows included.

`RosterTerminal` (`environment-terminal-roster.ts:16-20`) gains `presence?: string | null`: **`undefined` means the peer never published the key** (pre-presence host), `null`/empty means nobody attached. The mapper (`handlers/environment.ts:106-110`) must preserve that distinction, and it is a **format, not a copy** — W6 ships an object while `RosterTerminal.presence` is a string, so the mapping is `'presence' in terminal ? format(terminal.presence) : undefined`, never `presence: terminal.presence ?? null` (which would both lose the type and collapse "unknown" into "nobody"). `RosterRow` (`:34-44`) carries the same field. The formatter (`src/cli/environment-roster-format.ts:11-20`) prints `-` for "nobody" and **`presence?`** for "unknown" — the existing `capability-missing` idea (`environment-terminal-roster.ts:8-12`, `:119-122`) applied per-column instead of per-runtime. Never print "nobody" for "unknown". Update spec `notes`/`usage` (`src/cli/specs/environment.ts:24-34`; parity tests enforce spec↔handler alignment). `--environment` stays ignored for `environment *` (`src/cli/index.ts:22-32`).

### 2.5 Degradation matrix

| Pairing | Behavior |
| --- | --- |
| **New client / old host** | Subscribe carries `capabilities.presence: 1`; the old host's zod strips it (`terminal.ts:1060-1068`) and echoes no `presence`, so `supportsPresence` stays false and no chip renders. `terminal.list` ignores `includePresence` and omits `presence` on every row, so the CLI prints `presence?`. No `terminalPresence` events arrive. Nothing today is lost. |
| **Old client / new host** | **All four changes are suppressed** — W2 and W4 both require the W3(b) negotiation the client never sends; W6 without `includePresence` skips the boundary population pass entirely, returning the byte-identical payload; W8 is the exception worth naming: it is a broadcast with no negotiation, so a `terminalPresence` event — device labels included — **is sent to an old desktop subscriber and dropped unrendered** by the allowlist (`runtime-client-events.ts:83-96`). That is compat-legal under Rule 1 ("adding new ignorable event types", `protocol-version.ts:12-18`), so the honest claim is **no un-negotiated presence byte a client will render**, not zero bytes. Nothing today is lost. |
| **Mobile client / new host** | Mobile ships from `mobile/` on its own train and is allowlisted for `runtime.clientEvents.subscribe` (`runtime-rpc.ts:367`) and `terminal.multiplex` (`:416`), so it is a third skew axis — and the suppression is **not** uniform. W4 is structurally suppressed: it is emitted inside the `if (!isMobile)` branch (`terminal.ts:2726`, `:2741-2747`), so a mobile stream never sees it regardless of capabilities. **W2 is not** — the `subscribed` emit at `:2642-2659` runs 84 lines above that branch and fires for mobile streams too — so W2 relies on its own two gates (§2.2): the negotiation, and the host-observed requirement that the connection resolve to a runtime-scope participant, which a mobile grant never does (`device.scope`, `runtime-rpc.ts:1718`). W8 is filtered by `consumesPresence` in **both** the fan-out branch (`orca-runtime.ts:5256-5274`) and the subscribe snapshot guard (`client-events.ts:42-49`); without the second, the snapshot would leak the full roster on every mobile (re)subscribe. Belt-and-braces on W2 anyway: `isTerminalSubscribedResult` is structural and ignores extra keys (`mobile/src/transport/rpc-subscription-result-shapes.ts:1-10`). Per §2.1, **mobile participants appear in no B1 surface**. **W6 is the one presence surface with no mobile gate, and structurally cannot have one:** mobile is allowlisted for `terminal.list` (`runtime-rpc.ts:415`), population is gated solely on the `includePresence` param, and per gap 4 the handler is anonymous (`dispatcher.ts:44`) — there is no `clientKind` to branch on. A future mobile build that sent `includePresence: true` would pull desktop labels across the relay. B1 relies on no such build existing; **Q5 owns closing this**, and closing it means either identity on non-streaming dispatch or dropping `terminal.list` from the mobile allowlist. |
| **Relay transport** | The harness does not cover relay (`remote-wire-compatibility.md:98-101`), so reason it out. Presence adds no relay frame type and no field to `e2ee_auth` v2 (`mobile-e2ee-auth-validation.ts:13-26`). Relay is mobile-only (`mobile-relay-pairing-offer.ts:83-91`), and mobile is excluded by the runtime-scope rule on W2, structurally on W4, and by `consumesPresence` on W8 — **including the subscribe snapshot**, which is the one path that would otherwise put the largest presence payload across the relay. The added relay byte cost is zero *conditional on that snapshot guard*, which is why B2 test 2 asserts it directly. This also sidesteps the unestablished relay reap horizon (§2.1): a stale "in use by <phone>" chip cannot outlive the ~60 s figure in the UI copy, because no phone is ever shown. |
| **Mixed multi-client** | Negotiation is per-connection: a new desktop sees presence on its streams, an old desktop sees none — but the old one is still *counted*, because attachment is host-observed, not client-declared. One peer's shared-control + multiplex sockets appear as one entry (§2.1 aggregation). |
| **Shared-control down, multiplex up** | Roster stream is dead and unqueued (`runtime-client-events.ts:16-22`); pane chips keep working from their own streams. The renderer must not clear chips on roster loss. |
| **Multiplex reconnecting, shared-control up** | The roster still names the peer; the local pane shows nothing. This asymmetry is why W4 is authoritative per-PTY. |

## 3. Non-goals for B1

- **Presence is awareness, not enforcement.** No lock, no arbitration, no input rejection, no eviction. `isTerminalInputLockedForClient` stays mobile-only (`terminal.ts:284-297`), and the deliberate comment at `orca-runtime.ts:14078-14089` ("shared-control desktop viewers may still type alongside the host") stays true.
- **No change to width claiming.** `ClaimViewport` stays last-claim-wins (`orca-runtime.ts:14240-14249`); the width ping-pong two typists produce today (`pty-connection.ts:3939-3956`) becomes *visible*, not fixed.
- **No attempt to split two humans sharing one grant** (§2.1) — that is a pairing change, Q1.
- **Nothing persisted against `participantId`** (§2.1), and no presence state persisted at all.
- No new identity system, no rename UI, no per-device platform field, no mobile presence surface.
- No presence on `session.tabs`, no `RUNTIME_PROTOCOL_VERSION` bump.

1. *Negotiation positive.* Subscribe with `capabilities.presence: 1` → echo `{outputPause:1, presence:1}` **and** a `presence` object on `subscribed`; a second connection on the same PTY yields `terminal-presence` on both streams naming two participants.
2. *Negative control per guard* (mirroring `terminal-multiplex.test.ts:1640`): subscribe without `presence` → no echo key, **no `presence` on `subscribed`**, and zero `terminal-presence` events even while a peer attaches and types; a negotiated stream whose connection has **no tracked participant** (mobile-scope grant) still emits `subscribed` with **no `presence` key at all**; `terminal.list` without `includePresence` → deep-equal to the pre-change shape; a mobile-kind clientEvents listener receives no `terminalPresence` **and no presence entries in the subscribe snapshot** (assert on the snapshot path specifically, not only the fan-out); an unknown event type is dropped by `isRuntimeClientEvent`.
3. *Identity and aggregation.* Snapshot every emitted payload (W2, W4, W6, W8) and assert it contains neither a registry `token` nor a registry `deviceId`. Assert **one** `participantId` for two sockets of one grant, and — the double-count control — that a single peer holding a shared-control subscription *and* a multiplex stream yields exactly one W8 entry whose `attachedTerminals` is the union. Assert a different `participantId` after a simulated host restart, and that no persisted artifact anywhere contains one.
4. *Publication threshold and cleanup.* A one-shot request socket that opens, authenticates and closes with no subscription produces **no** W8 entry and no event. `detachStream` removes one attachment; `closeMultiplex` removes the connection's; closing one of a grant's two sockets keeps the participant (`mobile-socket-wiring.ts:213-218`); a stream that never registered a viewport still produces presence (closing the `terminal.ts:2587-2591` under-report gap — presence keys on the stream, not on `remoteDesktopViewers`).
5. *Typing TTL and stamp ordering.* Fake timers: the falling edge fires exactly once after 3 s; a 50-input burst emits at most `ceil(duration / 750)` events **and at least one per 2250 ms max-wait window** (the starvation cap the shared coalescer provides); and per §2.1, input rejected by `isTerminalInputLockedForClient` still flips `typing` true.
6. *Roster degradation and the W6 boundary invariant.* A peer omitting `presence` renders `presence?`; a capable peer with nobody attached emits `{ attachedCount: 0, participants: [] }` and renders `-`. **Assert the invariant on a fallback-path row specifically:** an orphaned/graph-less PTY that reaches `terminal.list` only through the `buildPtyTerminalSummary` loop (`orca-runtime.ts:15815`) must carry the key too, and a row whose `ptyId` is `null` must carry the empty object — a leaf-path-only test would pass while the path that dominates on a headless host silently violates it. `includePresence` survives an old-host schema parse untouched. Cover a folder workspace (no branch) and an SSH-scoped terminal so the column is workspace-agnostic.

## 5. Open questions for the owner

1. **Pending-grant collapse — answer before B2.** `getOrCreatePendingDevice` (`device-registry.ts:105`) can hand two humans one `deviceId`, and §2.1 forecloses disambiguating them inside presence (no socket-level fact to key on). So either (a) change pairing so each human gets a distinct grant — note `rotate: true` does not do this, it *drops* the other pending row (`device-registry.ts:134-141`), so this means a new always-mint path; or (b) accept that a shared grant reads as one person and say so in the pairing UI. B1 assumes (b) and treats (a) as a pairing-side change, not a presence change.
2. **Locking.** Should B1 or B2 add write arbitration for two desktops on one PTY — an input floor mirroring `beginMobileInputFloor`, or a soft "someone else is typing, press again"? This design assumes **no** — and inherits a constraint either way: per §2.1 any such arbitration must key on `pairedDeviceId`, never on the rotating `participantId`.
3. **Labels.** Every name today is a host-minted date string, so two humans paired the same day are indistinguishable — but `createPairingOffer` already accepts `args.name` (`runtime-rpc.ts:702`). Options, cheapest first: (a) a human-supplied name at pairing (`orca serve --pair-name "Ana's laptop"` plus a field in the desktop link flow) — **no wire change at all**; (b) accept the fallback and live with duplicates; (c) a host-side rename RPC + settings UI, the only option that fixes already-paired devices; (d) a client label on the **v1** `e2ee_auth` frame (safe for direct runtime-scope; v2 forbids extra keys, `mobile-e2ee-auth-validation.ts:13-26`). Q1 and Q3 are one conversation.
4. **Local/host attribution.** Per §1 gap 4 the anonymity is broader than "local callers": *no* non-streaming RPC carries identity (`dispatcher.ts:44`), so the host renderer, local `orca`, and any remote one-shot call all land in the same synthetic `host` participant. Show them as one `host` entry, or omit them — which would under-report the most common collision?
5. **Mobile in the roster.** §2.1 excludes mobile because the relay reap horizon is unestablished. Is establishing that horizon (relay-service side) worth doing so B2 can show phones, or is mobile permanently served by the existing driver-lock overlay? This question also owns the one ungated surface: W6 has no mobile gate available (§2.5), so whichever way it is answered, `terminal.list` presence for mobile callers must be decided with it.
6. **Typing at all.** 3000 ms TTL / 750 ms window / 2250 ms max-wait are guesses (the last two now inherited in shape from `SESSION_TABS_FLUSH_MS`/`SESSION_TABS_MAX_WAIT_MS`, scaled 15×). Is typing worth per-keystroke stamping in B1, or should B1 ship attachment-only presence (cheaper, no TTL machinery, no stamp-ordering decision) and add typing in B2?
7. **Roster scope.** `environment roster` already probes `local`, so the column reports this runtime's own attached peers too. Confirm that is wanted.
8. **Privacy opt-out.** Presence tells peer A that peer B is watching a specific terminal. Does a multi-tenant SSH host need `orca serve --no-presence`? With W2 gated, this is a single lever: add `terminal.presence.v1` to the `status.get` conditional filter (`orca-runtime.ts:5099-5107`) and every surface goes dark. Still worth deciding before B2 ships copy.
9. **`session.tabs` presence (W7).** Publishing per-device active tab gives a true who-is-where with no terminal attachment, but on a channel with no skew harness. Defer to B3, or in scope?
