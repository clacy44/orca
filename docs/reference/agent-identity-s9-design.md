# S9 — Agent identity on a shared host (design, rev 10, final)

Repo read-only at `/home/ubuntu/orca-integration` @ `feat/resilience-presence-integration` (B2 merged). Problem: two developers share one Linux box and one Unix user; each has several personal Claude accounts. Requirements as approved: **R1** a terminal's Claude credential is controlled only by the pairing grant that opened it; **R2** the opener switches among *their own* accounts live and every terminal they opened re-resolves with no restart; **R3** the other developer's terminals never move; **R4** both keep viewing/typing into each other's terminals (B2 presence shows the owner); **R5** account inventory stays on the owner's desktop. Accepted trade-off: the selected credential **is** materialized on the dev box, in that grant's own directory, `0600`, wiped when the grant's last connection closes and re-pushed on reconnect.

**R1 is achieved against remote *RPC* authority, not against a hostile paired peer.** A paired grant is shell-equivalent on this host today (§4). Read §4 before §2; the rest of the design is written to that limit and says so at each seam.

Evidence grade on every claim: **[code]** re-read at the cited line in this tree, **[doc]** from Claude Code documentation, **[inferred]** reasoned, not observed. All line numbers re-opened for rev 9, and every line rev 10 touches re-opened again.

## 1. What exists today

**One host, one credential file.** All Claude launches resolve through `ClaudeRuntimePathResolver.getRuntimePaths()` — `$CLAUDE_CONFIG_DIR` of the *Orca process* or `~/.claude` (`src/main/claude-accounts/runtime-paths.ts:14-25`) **[code]**. A switch writes the selected account's blob into that one file atomically at `0o600` (`runtime-auth-service.ts:421-422`, `:1732-1750`) **[code]** and merges the account identity into `.claude.json`'s `oauthAccount` (`:1576-1589`) **[code]**. Per-account storage is `<userData>/claude-accounts/<id>/auth/` holding exactly `.credentials.json` and `oauth-account.json`, guarded against symlinks, escapes and foreign ownership by a marker file (`managed-auth-path.ts:8-10`, `:12-57`, `:86-99`) **[code]**.

**A launch only gets Claude auth if its *command string* looks like Claude.** Both spawn paths compute `const isClaudeLaunch = !preAdoptedStablePane && !args.connectionId && isClaudeLaunchCommand(args.command)` (`ipc/pty.ts:4521-4522`, `:6122-6123`) over a regex on the command (`:1931-1938`), and `prepareClaudeAuth` runs **only** when that is true (`:4586-4587`, `:6168-6171`); otherwise `claudeAuth` is null and the spawn env is `sshScopedEnv` with no auth patch merged at all (`:4630-4632`, `:6186-6188`) **[code]**. `markClaudePtySpawned` is gated identically (`:5332-5334`, `:6948-6950`) **[code]**. Today this costs nothing — there is one credential file and `~/.claude` is the default for *every* process on the box, whatever launched it. Under lanes it is the single largest failure mode, and §2a is written around it.

**The live CLI re-reads the file.** Orca depends on this in two directions: read-back preserves tokens a running `claude` rotated into the runtime file before overwriting (`runtime-auth-service.ts:357-400`, persisted at `:387`) **[code]**, and managed refresh is *deferred* whenever any live Claude PTY exists, precisely because refreshing would double-rotate a single-use refresh token (`:406-419`, gate at `live-pty-gate.ts:84-86`) **[code]**. Both run inside `doSyncForCurrentSelection`, whose only drivers are `prepareForClaudeLaunch` (`:113-119`), `prepareForRateLimitFetch` (`:121-127`) and the constructor (`:110`) **[code]** — *a launch or a usage tick is what makes Orca look at the file at all*. That is the mechanism R2 keeps, and it is why the UI still hedges "Restart live Claude terminals before continuing old sessions" (`src/renderer/src/components/settings/AccountsPane.tsx:808`) **[code]**.

**The security gap, plainly.** `accounts.selectClaude` takes an account id and nothing else, and its handler ignores caller identity entirely (`src/main/runtime/rpc/methods/accounts.ts:113-117`) **[code]**; it rewrites the single host file. So **any** paired client — either developer's phone or desktop, any grant — moves the account under **every** live terminal on the box. Its siblings are equally open: `accounts.removeClaude` (`:137-141`), `accounts.selectCodex` (`:118-122`), `accounts.selectCodexForTarget` (`:123-130`), and the disclosure pair `accounts.list` (`:99-112`, snapshot at `:110`) and `accounts.subscribe`, which emits the whole snapshot at two points — the shared fan-out (`:184-186`) and the synchronous ready frame (`:209`) **[code]**. The two credential-capture RPCs are local-socket-only, refused for any identified socket (`:147-162`, refusal `:153-155`; `:163-175`, refusal `:167-169`) **[code]** — §2d shows why that guard is not enough once lanes exist. The auth-switch gate is process-global, so one person's switch blocks everyone's spawns (`live-pty-gate.ts:88-101`; read at four spawn sites, `ipc/pty.ts:4523`, `:4589`, `:6124`, `:6173`) **[code]**.

**Selection is keyed by `{runtime, wslDistro}` only** (`runtime-selection.ts:7-15`, `getSelectedClaudeAccountIdForTarget` `:44-50`) **[code]** — no per-caller dimension exists; one must be added.

**The plumbing precedent exists — and so does a recorded decision against it.** A per-launch `CLAUDE_CONFIG_DIR` already isolates WSL managed accounts: `getPreparation` returns `envPatch: { CLAUDE_CONFIG_DIR: activeAccount.wslLinuxAuthPath }` (`runtime-auth-service.ts:612-626`, patch at `:622`) **[code]**, and the launch path applies that patch last (`ipc/pty.ts:4630-4632`, mirrored `:6186-6188`) **[code]**. But Orca also wrote the opposite choice into its settings type — "persist only per-account auth (not a `CLAUDE_CONFIG_DIR` swap) so switching accounts doesn't fork Claude's shared chat/session context" (`shared/global-settings-types.ts:253`) **[code]**. §2a rebuts it explicitly and states what a lane loses; it is not an oversight.

**Claude Code semantics relied on** — and the two refused:
- `CLAUDE_CONFIG_DIR` relocates credentials, `settings.json`, `.claude.json`, session transcripts and memory as a unit **[doc]**; Orca already treats the co-located `.claude.json` as canonical when the dir is inherited (`runtime-paths.ts:27-33`) **[code]**.
- `.credentials.json` is a plain file at `0600` on Linux **[doc]**; on macOS the credential is a Keychain item whose service name is suffixed with the first 8 hex of `sha256(CLAUDE_CONFIG_DIR)` (`keychain.ts:85-93`) **[code]** — macOS isolates *by config dir already*.
- The running CLI re-reads `.credentials.json` rather than caching it for the process lifetime **[inferred from the two dependencies above; the single assumption R2 rests on, verified on the box in §5, with a stated fallback in §4 if it fails]**.
- **Deliberately not relied on:** `CLAUDE_CODE_OAUTH_TOKEN` (read once at start, restart to change **[doc]**) — Orca strips it and three siblings at launch (`environment.ts:1-6`; strip armed at `ipc/pty.ts:4737-4739` and `:6429-6431`) and *refuses* a managed launch that defines them (`ipc/pty.ts:4592-4596`, `:6176-6180`) **[code]**; and `apiKeyHelper`, which would be an elegant per-lane hook (re-run on TTL or 401 **[doc]**) but sends its output as both `X-Api-Key` and `Bearer` **[doc]**, has unconfirmed subscription-OAuth behavior **[doc]**, and outranks stored logins **[doc]** — a hijack primitive, not an isolation primitive. Orca has no `apiKeyHelper` in its own code and S9 keeps it that way.

## 2. Design — per-grant credential lanes

**Closure principle — stated once here, and every rule below is a consequence of it.** *For a lane launch, the effective Claude configuration (`CLAUDE_CONFIG_DIR`, auth env, CLI args, settings resolution, resume paths, hooks) is computed entirely host-side from lane-owned inputs. No client-supplied launch customization and no host-wide launch customization is honored for a lane launch unless it is (i) lane-scoped by construction or (ii) on an explicit allowlist with a stated reason.*

Eight review rounds each found a *different* way in. Rounds 1–6 found *surfaces* — `terminal.create` `env`, `session.tabs.createTerminal` `env`, `launchConfig.agentArgs`/`agentCommand`, `createManagedWorktree`, host-wide `settings.agentDefaultArgs`. Round 7 found something else: two whole **edges** the rule was not sitting on — the renderer-backed create that round-trips through `pty:spawn`, and the sleeping-agent wake that `worktree.activate` fires. Per-surface patching does not converge, and per-edge patching cannot converge either while the lane travels as a launch *value* that some edges carry and others drop. So the rule moves twice: **a lane launch is computed, not customized** (rev 7) — one host-side function *returns* the command, args, env, config dir and resume paths that spawn, and anything not on its allowlist never reaches the CLI — and **the lane is a property of the pane record, not of the launch request** (rev 8). Round 8 found the third kind: the rule was sitting one layer *above* the convergence — two host assembly points, while the env is rebuilt a third time inside the provider and one lane-scoped RPC (`session.tabs.createTerminal`) never reached the funnel at all. So rev 9 moves the anchor down to the three `provider.spawn` calls themselves and states what may run after it. A future launch-shaping input is closed by default; a future spawn *edge* is closed by default too, because it must read the lane from the pane it is spawning into. Round 9 proved that anchor complete by exhaustive grep and found no new surface: rev 10 changes one thing only — rev 9 stated its identity-drop over a *function* whose third caller is not a create, so the drop is now scoped to the two create call sites and the `session.tabs.activate` materialize gets its own stated disposition (§a(i), row 35).

**Rev 8's correction — where the lane lives; rev 9's — how far down enforcement has to sit.** Rev 7 threaded `laneGrantId` through launch options and enforced it at the host's two `ptyController.spawn` calls (`orca-runtime.ts:26520`, `:28208`) **[code]**. Both are real edges; both are *bypassable by a client flag*. `terminal.create` accepts `focus`, `rendererBacked` and `presentation` (`terminal.ts:1551-1554`, and note the schema types `rendererBacked`/`focus`/`activate` as `z.unknown().optional()` at `:1037-1039` — coerced only in the handler, which makes them unvalidated *and*, after this section, security-adjacent) **[code]**, and `shouldCreateInBackground` (`orca-runtime.ts:26356-26366`) **[code]** is false when either is set and a window exists — so the launch is shipped to the renderer over `terminal:requestTabCreate` (`:26739-26758`; a second dispatch in `runCreateMobileSessionTerminal` at `:27120`) **[code]**, queued as a tab startup command (`useIpcEvents.ts:1849-1863`) **[code]**, and spawned from the renderer through `ipcMain.handle('pty:spawn')` (`ipc/pty.ts:5870-5871`) **[code]**: a third spawn edge that carries no lane. Worse, with `worktree` omitted `workspace` is null and `resolveAgentTerminalCreateOptions` is never called at all (`:26705-26707`) **[code]**, so anything anchored “after” it never runs. A launch-option lane is an object a client can steer around. **Decision: the lane is a property of the pane record**, bound host-side when the pane is created and read back by pane identity at every spawn.

**Binding — host-side, at pane creation, from an authenticated request.** The background branch of `createTerminal` already mints `tabId`/`leafId` in main *before* the spawn, and says why: “mint tabId in main before spawn so paneKey is known at PTY env build time” (`orca-runtime.ts:26386-26400`, `makePaneKey` at `:26400`) **[code]**. That mint is the binding moment: `laneGrantId` is written into the lane registry keyed by `(worktreeId, paneKey)` before any launch input is assembled. Four consequences. **(i) A lane create never takes a renderer-minted pane — and there are two branches that mint one, not one.** First, `createTerminal`'s own renderer-backed branch: `focus`/`rendererBacked`/`presentation` are presentation preferences, not authority, and the background branch's own comment records that nothing is lost — “the spawned pane is still published and revealed with `activate`” (`:26361-26366`) **[code]**. The one thing that branch hard-requires is a resolvable selector, so a lane create with no workspace selector is **refused** `terminal.lane_requires_workspace`, mirroring the `startupAgent`-requires-selector throw the funnel already has (`:26343-26348`) **[code]**. Second — the round-8 blocker — `session.tabs.createTerminal` (`session-tabs.ts:55-58`, whose handler already reads `pairedDeviceId` at `:57`) → `createMobileSessionTerminal` (`orca-runtime.ts:26949`) → `runCreateMobileSessionTerminal` (`:27019`), whose branch key is **window presence, not a client flag**: `const win = this.getAvailableAuthoritativeWindow()` (`:27060`), `if (!win) return await this.createRuntimeOwnedMobileSessionTerminal(…)` (`:27061-27062`), otherwise `win.webContents.send('terminal:requestTabCreate', …)` (`:27120`) **[code]**. On this two-developer desktop box a window always exists, so that RPC *always* takes the renderer edge: the renderer mints the tab, replies with its own `tabId` (reply handler declared `:27102-27110`, the renderer `tabId` resolved at `:27115`), and spawns through `pty:spawn` under a paneKey with no binding row — which under rev 8's rule resolves to `shared`, i.e. the other developer's `~/.claude`. Its host fallback is no better: `:27186` passes `identity: { tabId: pendingSurface.tab.parentTabId, leafId … }` — a renderer-minted identity — into `createTerminal` at `:27339` **[code]**, so `canAdoptPaneIdentity` fires and the host mints nothing. **Decision: for a lane caller — a request over an identified socket whose grant holds a lane — the host branch is primary, unconditionally.** `createRuntimeOwnedMobileSessionTerminal` (`:27315`) **[code]** runs whether or not a window exists, and for a lane caller its `identity` argument is **dropped at its two *create* call sites, `:27062` and `:27186`, and at those only**, so the host mints `tabId`/`leafId` at `:26392-26400`, binds the lane there, and then publishes and reveals exactly as the background create does. A renderer-minted identity is never adopted into a lane **on a create**. **UX consequence, stated honestly:** this inverts the primary path of that one RPC for one caller class. The lane caller's tab is no longer created by the desktop renderer, so the optimistic tab shell the renderer publishes before the PTY spawns does not appear (`afterTabId`/`targetGroupId` are still honored by the host create); the tab surfaces in the desktop window a beat later, through publish/activate rather than at `tabCreateReply`; and the `tabId` returned to the mobile client is host-minted, so a client that cached the renderer's id sees a different one. A lane-**less** caller keeps today's path byte-for-byte. **The third call site is not a create, and the drop must not reach it — the round-9 MAJOR.** `:8124` sits in `activateMobileSessionTab` (`:8042`), reached by `session.tabs.activate` (`session-tabs.ts:38-41`, `pairedDeviceId` already in scope at `:41`) under `shouldMaterializePendingTerminal` (declared `:8089-8098`), and it passes `identity: { tabId: tab.parentTabId, leafId: tab.leafId, sessionId }` (`:8125-8129`) **[code]** precisely so an **existing** pane is reattached or respawned: `stableSessionId` is then `opts.identity.sessionId` rather than a fresh `serve-…` (`:27336-27337`), and the create runs `canAdoptPaneIdentity` → `adoptStablePane` (`:26419`). Dropping identity there would mint a new session and a second tab while the tapped one stayed non-ready forever — breaking the documented wake gesture (#11598, named in the comment at `:8092-8093`) for exactly the caller class lanes exist for. **Decision — the activate/materialize disposition, stated rather than left to the create rule:** `identity` is **kept** at `:8124` for every caller class; the materialize is gated by §a(ii)'s caller-class-independent predicate at `:26393-26400` and by nothing else, so it proceeds only when the pane's persisted lane *is* the caller's lane (otherwise refused `terminal.lane_not_owned`, before any spawn), and a respawn into that paneKey runs on the **pane's persisted lane** — never the caller's, never rewritten to `shared`. A pane bound **explicitly** to `{ kind: 'shared' }` — the automation path (`index.ts:2589`, rows 3 and 33) — draws the same refusal from a lane caller, because §a(ii)'s rule turns on the caller's own lane *being* that lane and a lane holder's is not the shared one. An **unbound** pane materialized by a lane caller is **refused** `terminal.lane_pane_unbound`, the fail-closed option, for the same reason the wake below refuses rather than resuming: materializing it would put a lane holder's agent tab on the shared `~/.claude` — the other developer's credential — silently, which is the downgrade this whole subsection exists to close, while the other option, promoting the unbound row to the caller's lane, would adopt a renderer-minted identity into a lane and contradict the create rule one clause above. Consequence, stated: a lane holder's pending tab minted before its lane existed (or by a lane-less path) stays non-ready and must be re-created; a lane-**less** caller's materialize is unchanged. **(ii) A client-hinted pane identity may not adopt a bound pane — for any caller class.** `terminal.create` forwards `tabId`/`leafId` hints (`terminal.ts:1555-1556`) **[code]** that the funnel validates into a paneKey (`canAdoptPaneIdentity` `:26393-26397`, `makePaneKey` `:26400`) **[code]** and then hands to `adoptStablePane` (`:26419`) **[code]**. The ownership check lands at **`:26393-26400`** — after the hint validates, **before** the adopt — and it is **caller-class-independent**: adopting a paneKey already bound to a lane is refused `terminal.lane_not_owned` unless the caller's own lane *is* that lane. A lane-less `{ kind: 'shared' }` caller may not adopt a lane-bound pane either, and a lane caller may not adopt a pane bound to another lane. **And the pane's persisted lane governs the respawn**, the case rev 8 left unsaid: when the PTY under a bound paneKey is dead or retired, `attachStablePaneOwner` retires it and returns null (`pty.ts:836-903`) and `spawnForStablePane` spawns **fresh** into that same paneKey (`:914`) **[code]** — that fresh spawn runs on the *record's* lane, so it happens for that lane's owner and for nobody else; for anyone else the adopt is refused before any spawn, and the binding row is **never** rewritten to `shared`. The activate/materialize path (row 35) rests on exactly this split: the predicate decides *whether* the materialize proceeds, the pane record decides *which* lane the respawn runs on. **(iii) The other creators bind the same way**: `createManagedWorktree` binds each pane it mints, `terminal.split` inherits from the parent record through the ownership predicate below, federated creates bind to the link's grant or fail closed, and the automation path passes `shared` explicitly. **(iv) The binding is persisted with the pane**, not merely held in memory (§h) — the rev-6 minor is now load-bearing, because cold restore and the wake have nothing else to read.

**And it is never accepted from the renderer.** `pty:spawn` args carry no lane field and one would be ignored if added: `pty.ts:6952` already calls `args` “untrusted IPC JSON” and bounds the paneKey it takes from them **[code]**. The renderer supplies *pane identity*, which the host validates against its own binding table; it never supplies *lane identity*. The residual is the one §2a case (ii) already concedes: a renderer that lies about which tab realized a create can aim an authorized create at a pane of its own — an anonymous local caller inheriting a lane, inside §4's envelope.

### (a) The lane, and how a launch gets pinned to one

A **lane** is one directory, `<userData>/claude-grants/<pairedDeviceId>/`, used verbatim as that grant's `CLAUDE_CONFIG_DIR`. It holds `.credentials.json`, `.claude.json`, `settings.json`, and — as a consequence of relocation **[doc]** — that grant's session transcripts. Directory `0700`, files `0600`. New module `src/main/claude-accounts/grant-credential-lane.ts` reuses the ownership discipline of `managed-auth-path.ts:12-57` (no symlinks, canonical containment under the root, exact relative-segment match, marker file) — re-parameterised for this key, not borrowed as-is: that check hardcodes a two-segment `<accountId>/auth` shape (`:37-44`) **[code]**. Lane ids are validated **at creation** against the exact `randomUUID` shape the registry mints (`device-registry.ts:92`) **[code]** — `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/` — so no grant id ever reaches `path.join` unvalidated; containment is defence-in-depth, not the primary check.

**Provisioning is an event, and no client can cause it.** A lane exists for grant G only after a **host-side consent action** — the local human ticks "give this device its own Claude account lane" on that device's row in the pairing/accounts UI, or runs the local `orca` equivalent over the Unix socket. It is the same class of act as approving the pairing itself. An `accounts.lane.push` naming a grant with no provisioned lane is **refused**, never auto-provisioning: otherwise any paired grant — including the other developer's phone — could flip host state that changes what *other* clients are allowed to do (§2d), which is exactly the cross-grant influence R1 exists to close. Deprovisioning is the same UI, and wipes (§f).

**Orphan reconciliation, gated on a registry read that actually succeeded.** At startup, walk `<userData>/claude-grants/` and delete any lane directory with no matching device entry — revoke-time wiping does not cover registry rebuilds or restore-from-backup. But `DeviceRegistry.load` wraps the whole read/normalize in a bare `try { … } catch { this.devices = [] }` (`device-registry.ts:334-365`, catch at `:363-365`) **[code]**, so a JSON parse error, a truncated write, or a `hardenExistingSecureFile` throw (`:340` — a real Windows ACL failure mode) yields **zero** devices. Unconditional reconciliation would then delete *every* lane on the host, including the transcripts §f deliberately preserves and the watermarks §f keeps through a wipe. **Decision:** `load` records a `loadSucceeded` flag; reconciliation runs only when it is true **and** the registry is non-empty, and otherwise logs and deletes nothing. Negative control in §5.

**A grant is not automatically one human, and provisioning must refuse the ones that are not.** The whole authority model keys on `pairedDeviceId`, but the ordinary regenerate-QR link *coalesces*: `getOrCreatePendingDevice` returns the first never-scanned entry of that scope instead of minting (`device-registry.ts:115-133`, the find at `:122-126`) **[code]**, and the registry states the consequence itself — "two humans handed one coalesced link land on one deviceId and one token, so nothing downstream can tell them apart. A grant can only be split per person at offer time" (`:135-138`) **[code]**. If the two developers paired through that link they share one `deviceId`, therefore one lane; either one's switch moves the other's terminals, **R3 fails silently**. B2's per-person path is `mintPendingDevice`, which never reuses a pending row and stamps a deadline (`:139-157`; `pendingExpiresAt` written at `:99-100`) **[code]**. **Decision:** lane provisioning **refuses** a device entry that carries no `pendingExpiresAt`. That field is the durable discriminator — written at mint, surviving scanning, whereas `isMintedPendingDevice` additionally requires `lastSeenAt === 0` and stops matching the moment the person connects (`device-registry-pending-grants.ts:14-16`) **[code]**. Consequence, stated: a pre-B2 or coalesced grant cannot hold a lane until it is re-paired per person — the correct failure, because nothing on the host can tell whether such a row is one human or two.

**The lane env must NOT be gated on the launch command. This is the correction rev 5 most needed.** Rev 5 threaded `laneGrantId` into `prepareClaudeAuth` and stopped — but `prepareClaudeAuth` is reached only when `isClaudeLaunch` is true (`pty.ts:4586-4587`, `:6168-6171`, predicate `:4521-4522`/`:6122-6123` over the regex at `:1931-1938`) **[code]**. So a lane-pinned pane created as a plain shell — bare `terminal.create` with no `command`, `session.tabs.createTerminal`, a worktree default tab, any non-Claude `startupAgent` — would receive **no** lane env, and the human typing `claude` at that prompt would resolve `~/.claude` (`runtime-paths.ts:14-25`) **[code]**: on this box, the other developer's credential. Meanwhile §h would still render the pane `credentialLane: 'grant'` from its `laneGrantId` and §k would attribute its statusline usage to the lane owner — silent misattribution, the exact mode the funnel exists to prevent. **Decision: decouple.** A lane-pinned spawn (`credentialLane.kind === 'grant'`, no `args.connectionId`, normalized target runtime `host`) gets the lane `envPatch` **regardless of `args.command`**; `isClaudeLaunchCommand` keeps its existing jobs and gains a lane arm. Three consequences, all deliberate:
1. `stripAuthEnv: true` now arms on **every** lane pane, so `hasClaudeAuthEnvConflict` (`environment.ts:37-45`) **[code]** refuses a lane pane that defines Anthropic auth vars and `authEnvToDelete` (`pty.ts:4737-4739`, `:6429-6431`) **[code]** deletes them from it. That is a behavior change for plain shells in a lane, and the right one.
2. `markClaudePtySpawned` (`pty.ts:5332-5334`, `:6948-6950`) **[code]** keeps its command-detected arm **and** additionally registers every lane-pinned pane into that lane's "may hold lane credentials" set, because the human can type `claude` at any prompt. Deliberately conservative: it over-defers rotation (§e) rather than risk a double rotation. The cost — a lane whose panes never run `claude` never gets a *host* rotation — is absorbed by the CLI's own refresh plus §c's `cli-observed` receipt, and it is what makes §f's "a lane launch fails closed when the lane is unloaded" true for ordinary panes.
3. The second Claude-compatible runtime, **OpenClaude**, is missed by the command regex entirely (`openclaude` has no path separator before `claude`, so `:1931-1938` cannot match), and decoupling gives it the lane *env* where a command regex never could. **But rev 7's “covers it for free” claimed isolation, and rev 8 grades that claim: it is unsupported.** Orca's own OpenClaude integration hardcodes `configDirName: '.openclaude'` (`claude/hook-settings.ts:28-31`), resolved as `join(homedir(), configDirName, 'settings.json')` (`:71-73`) **[code]**, and the tree contains no `OPENCLAUDE_CONFIG_DIR` and no config-dir env for it at all — `grep -rn "OPENCLAUDE_" src` returns three hits, all that one constant **[code]**. Whether the binary honors `CLAUDE_CONFIG_DIR` is **[inferred] and unverified**, so the design refuses the assumption instead of resting on it: if it does not, an OpenClaude pane in a lane shares one credential store across grants while §h renders `credentialLane: 'grant'` and §k bills the usage to the lane owner — the worst class in this design. **Decision, fail closed:** the host **refuses to build an OpenClaude launch for a lane pane** (`terminal.lane_agent_unsupported`), and lane provisioning marks OpenClaude unavailable *in that lane* — a lane-scoped, host-computed version of row 15's disable. Named residual in §4, control in §5, and a §5 live step settles the question on the pinned binary — if OpenClaude does honor `CLAUDE_CONFIG_DIR`, this item collapses to one allowlist line.

**Lane derivation *and binding* live at the `createTerminal` funnel, not at one handler.** `runtime.createTerminal` (`orca-runtime.ts:26339-26341`) **[code]** has **twenty** production call sites — fourteen `this.createTerminal(...)` inside `orca-runtime.ts` (`:17221`, `:22413`, `:22472`, `:22506`, `:22788`, `:22829`, `:23541`, `:23662`, `:23888`, `:24010`, `:26096`, `:26280`, `:26906`, `:27339`) plus `terminal.ts:1536`, `coordinator.ts:375`, `orchestration-worker-topology.ts:64`, `orchestration-federation.ts:165` and `ipc/worktree-remote.ts:315`/`:365` **[code]** — and several are reachable by a paired grant. **S9a makes `credentialLane` a required field of `TerminalCreateOptions`** (`orca-runtime.ts:1435-1482`) **[code]**: `{ kind: 'grant', grantId } | { kind: 'shared' } | { kind: 'inherit', fromPtyId }`. ### (b) What the desktop pushes

The owner's desktop pushes **the selected account only**: the byte contents of that account's `.credentials.json` and `oauth-account.json` from `<userData>/claude-accounts/<id>/auth/` — the two filenames Orca already reads and writes (`managed-auth-path.ts:59-72`, `:74-84`) **[code]**. From `oauth-account.json` the host needs, and stores, only what it already parses: `accountUuid`/`accountId`, `emailAddress`/`email`, `organizationUuid`/`organizationId` (`runtime-auth-service.ts:963-976`) **[code]** — enough to merge `oauthAccount` into the lane's `.claude.json`, enforce §e's residency invariant, and render an identity label. The host never receives the owner's account **list**, ids of unselected accounts, usage rows, or the desktop's store.

**Payload validation, before any byte reaches the lane.** The envelope has exactly these two members and no others, each bounded (≤64 KiB); `.credentials.json` must parse and satisfy the shape predicate Orca already uses — a `claudeAiOauth` object with a non-empty `accessToken` (`runtime-auth-service.ts:871-879`) **[code]**, extracted so both callers share it — and `oauth-account.json` must parse to a JSON object. Anything else is refused `accounts.lane.push_malformed` **before** the `0600` write, so a well-formed-envelope-but-garbage blob fails at the RPC and not at the next launch.

**And the account identity is client-asserted.** Everything the host knows about *whose* account this is comes from the pushed `oauth-account.json` (`:963-976`) **[code]**; a pusher can put any email in it. The **grant/owner** label is host-observed from `pairedDeviceId` and is not spoofable; the **account email** is. Q3 asks whether the other developer should see the email at all, and this is the reason it matters.

### (c) A live switch is a push — and something must re-read the lane

Switching on the desktop pushes the newly selected blob into the same lane. The host writes it atomically at `0o600` and merges `oauthAccount` into the lane's `.claude.json`. No PTY restart, no notification to the CLI: every live `claude` in that lane re-resolves on its next credential read, exactly as today's host-wide switch does; every terminal in another lane, and in the shared lane, is untouched because their `CLAUDE_CONFIG_DIR` points elsewhere. R2 and R3 become one property: *the write is scoped to the directory the launch was pinned to*. There is no separate remote "selection" RPC to secure.

**But a writer alone is not enough.** Today's protection against clobbering a CLI-rotated token is the read-back inside `doSyncForCurrentSelection` (`runtime-auth-service.ts:357-400`, persisted at `:387`) **[code]**, driven by launches and usage ticks (`:113-127`) **[code]**. A lane whose writer "does nothing else" never observes a rotation performed by the lane's *own* live `claude`: the desktop's copy goes stale, and the ordinary post-wipe reconnect re-push (§f) then restores an already-revoked blob, after which every terminal in that lane fails `invalid_grant`. **S9b therefore ships a lane sync driver**, `syncLane(laneId)`, the per-lane analogue of `doSyncForCurrentSelection`, on exactly four triggers: (1) before any launch pinned to that lane (the lane arm of `prepareForClaudeLaunch`, `:113-119`), (2) on each rate-limit tick for a lane with live PTYs (`prepareForRateLimitFetch`, `:121-127`), (3) immediately before applying a push, (4) once per lane at startup, before the wipe (§f). **Trigger (4) is observe-only** — it compares, emits the receipt and records the watermark, and never rotates; §e says why. It compares the lane file's refresh token against the lane's last-written value using the existing comparator (`readRefreshTokenFromCredentials` `:953-961`, `compareRefreshTokens` `:941-951`) **[code]**; a difference means the lane's CLI rotated, so **the receipt covers CLI-observed rotation, not only host-initiated rotation**.

**The watermark has three writers, not one — and rev 5 named only the first.** `syncLane` records it (triggers 1–4); a **successful push** sets it to the pushed blob's refresh-token sha256; and every rotation receipt (`host` or `cli-observed`) sets it to the rotated token's sha. Without the push arm the freshness rule in §e eats itself: `syncLane` runs immediately before applying a push (trigger 3) and records the *pre-push* file's sha, so the next push — which carries `basedOn` = the sha it pushed last time — would mismatch, be refused `accounts.lane.push_stale`, and **R2 would work exactly once per lane**. Ordering: validate → freshness-check against the current watermark → write → set the watermark to the new sha, all under the lane's write queue and the lane's switch gate (§f).

**The two writers cannot be reused as-is.** `writeRuntimeCredentials(contents)` is private and opens with `const credentialsPath = this.pathResolver.getRuntimePaths().credentialsPath` (`:1732-1733`) while mutating the shared `lastWrittenCredentialsJson` (`:1749`); `writeRuntimeOauthAccount(oauthAccount)` opens with `const configPath = this.pathResolver.getRuntimePaths().configPath` (`:1576-1577`) **[code]**. Neither takes a path, and there are 17 `getRuntimePaths()` call sites in this one file **[code]**. The reusable primitive is `writeFileAtomically(path, contents, { mode: 0o600 })` from `codex-accounts/fs-utils` (imported at `:8`, used at `:1748` and at `managed-auth-path.ts:4`, `:83`) **[code]**. **Decision:** the lane writer is a new file calling that primitive directly and owning its own per-lane last-written cache; `runtime-auth-service.ts` gets a path-taking extraction budgeted in S9b (§6), not an in-place widening — AGENTS.md forbids disabling `max-lines` (`AGENTS.md:14-16`) **[code]**.

### (d) Authorization

Lane RPCs derive their target lane from `ctx.pairedDeviceId` **only** — never from a parameter, and the params schema has no lane field to spoof. This is the pattern the Run mailbox already argues explicitly (`rpc/methods/orchestration-remote-run-mailbox.ts:11-22`) **[code]**. Anonymous callers are refused: a Unix-socket caller cannot address a lane at all.

**Every refusal below is conditioned on the *caller's own* lane state, never on "some lane exists on this host."** A host-global dormancy switch would let one grant's single RPC downgrade what every other client may do — the cross-grant influence §a's provisioning rule closes.

- `accounts.selectClaude` (`accounts.ts:113-117`) materializes the chosen account into the shared `~/.claude` (`runtime-auth-service.ts:421-422`) **[code]** and is gated on **two independent conditions, checked in this order**. *Caller scope:* **anonymous local callers** unchanged and host-wide (this is `orca account select` and the host's own renderer); **identified callers with no provisioned lane** unchanged and host-wide — they own no lane, their terminals are in the shared lane, and today's semantics are right for them; **identified callers that hold a lane** — **refused** `accounts.selection_out_of_scope`, telling them to switch in their own lane. Not silently rescoped: a client that today believes it moved the host must not believe it moved something it did not. *Target residency — L1's second edge:* **for every caller class, including the anonymous local one, the call is refused `accounts.lane.account_resident_elsewhere` when the target account is resident in any lane.** Without this, the ordinary pre-S9 state (both developers' accounts already in `<userData>/claude-accounts/`) lets a lane-**less** peer — or either developer's local shell, or the renderer — call `selectClaude(X)` after A pushed X into A's lane and re-create the exact double residency L1 exists to prevent, single-use refresh token and all. The check is the same predicate `removeClaude` uses, written once as `assertNotLaneResident(accountId)` over §e's index and called from `selectClaude`, `removeClaude` and `accounts.lane.push`; the refusal message names the holding grant's presence label and the remedy (`accounts.lane.clear`).
- `accounts.removeClaude` (`:137-141`): refused for an identified caller when the target account is **resident in any lane** (target-scoped, not host-scoped) — deleting it would strand a live lane. Unrelated accounts remain removable.
- `accounts.addClaudeFromConfigDir` (`:147-162`) and `accounts.addCodexFromHome` (`:163-175`) are **not** safe as they stand. Their `clientKind` guard refuses identified sockets but not anonymous local callers (`:153-155`, `:167-169`) **[code]** — and on this box the anonymous local caller is *either developer*, same Unix user. `captureFromExistingConfigDir` accepts any resolved path containing `.credentials.json` with no containment check (`claude-accounts/service.ts:205-245`, resolve at `:213`) **[code]**, then `writeClaudeManagedAuthFile` copies the blob into `<userData>/claude-accounts/<newId>/auth/` permanently (`:811-822` esp. `:820`; `:824-835` esp. `:830`) **[code]**, after which `selectClaude` makes it host-wide. So `orca account add --config-dir <userData>/claude-grants/<A>` converts a co-tenant's momentary read (§4) into permanent host-managed possession — defeating the wipe promise with one supported command. **Fix (S9a):** refuse a `configDir` whose **canonical** path is the `claude-grants` root or under it, and mirror it for `addCodexFromHome`'s `sourceHome`. A path-level test is not enough: `captureFromExistingConfigDir` calls `resolve(trimmed)` at `:213` and the next check follows symlinks through `existsSync` at `:217` **[code]**, so `--config-dir /tmp/decoy` linking into a lane would defeat a `startsWith` on the resolved string. The check canonicalizes exactly as `managed-auth-path.ts` does — refuse a symlink outright (`:23-25`), `realpathSync` both sides (`:26-27`), then `startsWith(canonicalRoot + sep)` (`:28-32`) **[code]**.
- `accounts.list` (`:99-112`) and `accounts.subscribe` (`:179-213`) are wholly unscoped disclosure paths: today grant B receives the host's full account snapshot including emails and usage. `subscribe` is identity-blind by construction — it destructures only `{ runtime, connectionId }` (`:182`) and emits `runtime.getAccountsSnapshot()` verbatim at **both** the fan-out (`:184-186`) and the ready frame (`:209`) **[code]**. S9b newly destructures `pairedDeviceId` and converts the shared snapshot into a per-connection **projection** at both emit points as well as in `list`. The projection shows (i) host/shared-lane accounts and (ii) the caller's own lane row, whose usage comes from §k; another grant's lane appears only as an opaque `occupied` boolean with the grant's presence label. With zero lanes the projection is byte-identical to today's snapshot.

Compatibility consequence, in full: a paired client **loses** host-wide Claude switching exactly when it has been given its own lane — i.e. only after the local human granted it one. A grant with no lane keeps everything it has today, including (residual, §4) the ability to move the shared lane under lane-less peers — for accounts that are **not** resident in a lane; that one exception applies to every caller class. Q1 asks whether the owner's *own* second grant may drive their primary lane; Q5 asks whether the shared lane should be lockable too.

### (e) Refresh — the host rotates, keyed by account, not by lane

**Decision: the host.** Refresh tokens are single-use; a double rotation revokes one copy. Only the host can observe the fact that makes rotation safe — whether a live `claude` holds that credential — and it already encodes that: rotate only when no live PTY holds the creds, otherwise defer and let read-back preserve whatever the CLI rotated (`runtime-auth-service.ts:406-419`, `:357-400`) **[code]**. The desktop cannot see that and would race the CLI.

**Which store a lane rotation writes to.** Not managed storage: `refreshManagedAccountTokenIfNeeded` (`:1044-1062`) persists through `writeManagedCredentials(account, …)` (`:1021-1034`), which requires a `ClaudeManagedAccount` and an Orca-owned `<userData>/claude-accounts/<id>/auth` path (`:1025-1027`; the service-side twin asserts the same at `claude-accounts/service.ts:811-822` esp. `:816`) **[code]** — and §b is explicit that the host never receives the owner's account store, so a lane account has **no** managed record to persist into. S9b's lane rotation therefore calls the shared network primitive `refreshClaudeOauthCredentials(credentialsJson)` (used at `:1051`) **[code]** and persists through §c's lane writer into the lane's own `.credentials.json`, then emits the receipt and moves the watermark. **Trigger:** the §c sync driver on (1)–(3) — launch, rate-limit tick, pre-push — and **not** on (4). The startup pass must be observe-only because it runs *before* `seedLiveClaudePtysFromPersistence`, and `index.ts:2240` states that ordering invariant in so many words — "run before `ClaudeRuntimeAuthService`'s constructor sync — a surviving daemon Claude CLI holds the single-use refresh token; early refresh rotates it out mid-session" (seeded `:2248-2249`, reconciled `daemon/daemon-init.ts:1043-1061`) **[code]**. At that instant the lane-scoped liveness query is empty by construction, so a rotating startup pass would hand that lane `invalid_grant` across every live session in it. There is no separate timer.

**Invariant L1 — one account, at most one lane.** The single-use-refresh invariant is per **account**, so keying rotation by *lane* is unsound: nothing otherwise stops account X being resident in grant A's lane and grant B's lane (or in a lane and the shared lane), and the host — the only party that can see both — would rotate X on B's behalf while A's live `claude` holds it. The docstring on the rotation path states the precondition a per-lane split would break (`:1041-1043`) **[code]**. **Therefore:** the host maintains a residency index and refuses **both** edges through one predicate, `assertNotLaneResident(accountId)`, stated once in §d and called from `accounts.lane.push`, `accounts.selectClaude` (every caller class, including anonymous local) and `accounts.removeClaude` — `accounts.lane.account_resident_elsewhere`, naming the holding grant's presence label. It keys **rotation, deferral and the refresh serialization axis by account across all lanes** — never by lane. `managedRefreshDeferredByLivePtyAccountId` (`:106`) is already account-keyed **[code]** and stays that way; what becomes lane-aware is only the *liveness query* feeding it, single-valued precisely because of L1 — and, per §a consequence 2, fed by every lane-pinned pane, not only command-detected Claude launches.

**The index's `host` row cannot come from the managed account, because usually there isn't one.** The shared lane legitimately holds an **unmanaged system login**: `runtime-paths.ts:14-25` resolves `~/.claude`, and `getPreparation`'s host branch returns `provenance: 'system'` with `stripAuthEnv: false` whenever `activeAccountId` is null (`:655-670`) **[code]**. That is the default on a box where nobody ran `orca account add`. With no host row, a lane push of the very account whose refresh token is live in `~/.claude` is accepted, the single-use token is resident in two config dirs, and an `accountUuid`-keyed axis cannot see the unmanaged side. **Fix:** the index derives its `host` row from the shared lane's files directly — identity via `readIdentityFromOauthAccount(readRuntimeOauthAccount())` (`:963-976`, `:1548-1563`) **[code]**, plus, because an unmanaged login may carry no `oauthAccount`, a second residency key of `sha256(readRefreshTokenFromCredentials(<shared .credentials.json>))` (`:953-961`) **[code]**. A push is refused if **either** key collides. Every lane row carries both keys. **And the `host` row is re-derived, not merely seeded at startup:** it is recomputed on every shared-lane `doSyncForCurrentSelection` (launch and rate-limit tick, `:113-127`) **[code]** and immediately before each `selectClaude`, `removeClaude` and push residency check — otherwise an external `claude login` into `~/.claude`, or a `selectClaude` landing between two syncs, produces a collision nothing observes. Reading two small files on those paths is the same cost the sync already pays.

**The desktop must be explicitly suppressed.** The owner's desktop runs its own `ClaudeRuntimeAuthService` over the same managed account — it must, to have selected and pushed it. Its rotation is gated only by `hasLiveClaudePtys()` (`:407`), a module-global set fed exclusively by that machine's own spawns (`markClaudePtySpawned` is called only from `pty.ts:5333` and `:6949`) **[code]**. The desktop cannot see the host lane's live PTYs, so whenever no local `claude` runs and the token is expiring it calls `refreshManagedAccountTokenIfNeeded` (`:412-415`) **[code]** and rotates the token out from under the lane. **S9b adds a delegation lease:** while an account is `delegatedToLane: { hostId, grantId, since }`, (i) the desktop's `refreshManagedAccountTokenIfNeeded` is a no-op for it, (ii) the desktop refuses its own managed launches under it, and (iii) the lane's rotation receipt is the only writer of that account's stored credential. **The lease is durable, not process-local:** persisted in the desktop's own store, reloaded at start, released only by an explicit `accounts.lane.clear`, a grant revoke, or expiry — never by a desktop restart or a dropped connection.

**The lease closes one install, and only one — R-DR2, named.** Rev 5 justified the gap with "the lease is per-desktop and cannot see other desktops' leases — which is why L1 is enforced host-side, where both lanes are visible." That is a non-sequitur: L1's residency index can only enumerate lanes **on this host**. A *second copy* of account X in another machine's managed store — the human's laptop, a reinstall, or a desktop on an old build with no lease code — runs the unmodified gate `if (!liveClaudePtys) { refreshManagedAccountTokenIfNeeded(…) }` (`:407`, `:411-419`) **[code]** over a live-PTY set fed only by that machine's own spawns, and rotates the single-use token out from under the lane; every live terminal there then fails `invalid_grant`. §c's receipt/pull path can observe it, never prevent it. **No host-side control exists** — the host cannot reach another machine's store. What ships is detection and recovery: the pushed envelope carries `delegation: { hostId, grantId, since }`; `syncLane` treats an unexpected sha change whose refresh then fails as `laneState: 'reauth-required'` with a receipt naming the cause; and the desktop UI states the operating rule — *an account delegated to a host must not be live in another Orca install*. Accepted residual, in §4 and in the degradation matrix.

**Per-lane state is bigger than it looks.** `ClaudeRuntimeAuthService` holds eight mutable process-global fields (`:98-106`) **[code]**. Three consequences: (1) `lastWrittenOauthAccount`/`hasLastWrittenOauthAccount` (`:103-104`) gate the `.claude.json` identity write, so a lane push that updates them makes a later **host** sync see "already written" and skip — the host `.claude.json` would then report grant A's account, the exact misattribution R1 exists to prevent; (2) `skipNextReadBackForAccountId` (`:105`) is keyed by **account**, so the re-key must be `(lane, account)`; (3) the single `mutationQueue` (`:98`) would serialize all lanes' pushes head-of-line — each lane gets its own write queue, with rotation still serialized per account.

**Push freshness, honestly.** (1) The host rejects a push whose `basedOnRefreshTokenSha256` does not match the lane's current **watermark** — as maintained by all three writers in §c — unless marked `reauthenticated: true`; that flag is client-asserted and therefore advisory, so the host additionally compares issued-at/expiry and refuses a strictly older push. (2) An **empty** lane is not a blanket exemption: an empty lane whose watermark is present is checked against it exactly as a loaded lane is; only a lane with *no* watermark (never pushed, or deprovisioned and re-provisioned) accepts any well-formed push. (3) The host emits a secretless rotation receipt (identity, refresh-token sha256, `expiresAt`, cause `host` | `cli-observed` | `foreign-rotation`) on the lane status stream, and the desktop pulls the rotated blob back over the same grant-scoped channel — the mirror of Orca's existing read-back-to-managed-storage (`:362-364`, `:387`) **[code]**.

### (f) Lifecycle

Lane credential files are wiped when the grant's **last** connection closes. B2 computes that predicate: `handleClose` reports `hasOtherConnections` (`rpc/mobile-socket-wiring.ts:209-221`, comparison `:215-219` esp. `:218`) and `runtime-rpc.ts:1384` branches on `!hasOtherConnections`, calling `onClientDisconnected(socket.device.deviceToken)` at `:1385` **[code]**. **Key mismatch to note explicitly:** that path compares and passes `device.deviceToken`, while lanes are keyed by `pairedDeviceId`, which is `device.deviceId` (`runtime-rpc.ts:1360`) **[code]**. `socket.device.deviceId` is in scope at the wipe site, and the wipe must read that, not the token it is handed.

**Wiping at close is not enough: it must also happen at startup.** Close detection rides `transport.onConnectionClose` (`mobile-socket-wiring.ts:102`) **[code]**, and a crash, `kill`, or ordinary quit never runs that handler — so a lane's `.credentials.json` would otherwise stay resident with no grant connected until some *future* connection happens to close. Orphan reconciliation (§a) does not cover it: a still-paired grant's lane has a matching device entry.

**The startup wipe has a trap of its own, and the watermark defuses it.** `seedLiveClaudePtysFromPersistence` exists precisely because a daemon-hosted `claude` survives an Orca restart still holding the single-use refresh token (`index.ts:2240` comment, seeded `:2248-2249`, reconciled `daemon/daemon-init.ts:1043-1061`) **[code]**. If S9c wipes lanes and the reconnecting grant then pushes into a lane that accepts anything because it is empty, an older desktop blob lands under a surviving daemon session that has since rotated. **Fix:** the startup sequence is (1) an **observe-only** `syncLane` over each resident lane — compare, emit the receipt, record the **watermark**, never rotate (§e) — the watermark being a secretless `{ laneId, identity, refreshTokenSha256, expiresAt }` row persisted beside the live-PTY session ids; (2) wipe the credential material; (3) seed the live-PTY gate; (4) bind the listener. A re-push is then checked against the watermark even though the lane is empty (§e rule 2), so the stale blob is refused `accounts.lane.push_stale`. This is the same reason the persisted live-PTY rows gain a lane id (§3 row 6): a seed with no lane attribution defers **all** accounts until `confirmSeededClaudeLivePtys` resolves it (`live-pty-gate.ts:40-45`, `:57-68`) **[code]**.

**Residency window, stated next to the promise:** the credential is resident from push until the earliest of last-close, idle/keepalive timeout, or the next Orca start; a half-open TCP connection that never emits close extends it to the idle timeout. §4 concedes a co-tenant can read the file at any resident moment; the UI states the window rather than promising instant removal.

Wipe = **sweep the lane directory for credential artifacts**, not delete one filename: `.credentials.json` plus every `.credentials.json.*.tmp` and any other stray `*.tmp` sibling. `writeFileAtomically` stages at `${targetPath}.${process.pid}.${randomUUID()}.tmp` (`codex-accounts/fs-utils.ts:12`) and unlinks it only on a *thrown* error (`:17`) **[code]**, so a crash between the `writeFileSync` at `:14` and the rename at `:15` leaves a full-credential blob at `0600` under a name a filename-scoped wipe never touches. Lane **open** sweeps too. Then delete the `oauthAccount` key from the lane's `.claude.json` (plus the lane's scoped Keychain item on macOS, §i), drop the lane's rows from §e's residency index, and **keep** the watermark. The lane dir, its `settings.json`, its mirrored memory and its transcripts survive — they are not secrets, and destroying transcripts on dropped Wi-Fi would be hostile. On reconnect the desktop re-pushes; until it does, a lane launch **fails closed** ("your account is not loaded on this host"), never silently falling back to the shared lane. On grant revoke, the whole lane directory *and* its watermark are removed — hooked beside the existing `terminalPresenceRegistry.forgetGrant(deviceId)` calls (`runtime-rpc.ts:645`, `:658`) **[code]**.

**The gate becomes per-lane.** `beginClaudeAuthSwitch`/`isClaudeAuthSwitchInProgress` are module-global booleans (`live-pty-gate.ts:88-101`) and `liveClaudePtyIds` is one global set (`:1`) **[code]**. S9c keys both by lane id (`'host'` for the shared lane, mirroring B2's reserved attachment key at `terminal-presence-registry.ts:10`) **[code]**, so one developer's switch blocks only their own spawns; the four spawn-side reads (`ipc/pty.ts:4523`, `:4589`, `:6124`, `:6173`) **[code]** become lane-scoped with them — and, per §a, their condition widens from `isClaudeLaunch` to `isClaudeLaunch || lanePinned`, so a push blocks the plain-shell panes that now carry lane credentials too. **And `accounts.lane.push` must take that gate.** `beginClaudeAuthSwitch` has exactly one caller today — `syncRuntimeAuthWithLivePtyGate` (`claude-accounts/service.ts:560-570`, call at `:564`) **[code]** — the *host* switch path; a lane switch is a push and never passes through it, so without this a push races spawns in its own lane. The push handler wraps its lane write in `begin`/`endClaudeAuthSwitch(laneId)`. Control: a spawn in lane A during a push to lane A is refused — including a plain-shell lane pane; a spawn in lane B during the same push is not. Lane is the right key for the *spawn gate*; it is **not** the key for refresh — the refresh path asks "is a live PTY running in the lane where this account is resident", resolved through §e's residency index, single-valued by L1.

### (g) Handoff — narrowly defined, mostly scoped out

**Shipped (S9d):** `terminal.openInMyLane` — grant-scoped, creates a **new** terminal in the same workspace (git worktree *or* folder workspace, `AGENTS.md:43-45`) **[code]**, under the caller's lane, optionally seeded with a plain-text prompt. It moves no process and copies no files. A caller with **no** lane is **refused**, never silently served from the shared lane; the seed prompt is bounded (≤4096 bytes, control characters other than newline rejected) and delivered as terminal input, never interpolated into a shell command line.

**The authorization check is a real join.** `registerConnection` (`terminal-presence-registry.ts:111-124`) stores into `participants`, a map keyed by **connectionId** (`:49`, set at `:121`), and it is called for *any* authenticated socket (`runtime-rpc.ts:1352-1363`, comment `:1353-1357`) **[code]** — so "is the caller a registered participant" is true for every connected grant on every terminal and authorizes nothing. Per-terminal membership lives in `attachments`, ptyId → subscriptionKey → attachment (`:50`, `attachmentsFor` `:218-225`, `attach` `:227-233`, public reader `attachmentsOf` `:264`) **[code]**. **The check S9d ships:** `attachmentsOf(ptyId)` → each attachment's `connectionId` (`:23-26`) → `participants.get(connectionId)` → `.pairedDeviceId` must equal `ctx.pairedDeviceId`. That needs one new registry accessor (`grantsAttachedTo(ptyId)`) because `participants` is private.

**Scoped out — not built, and not the same as not reachable.** Transcript-seeded "continue this session in my account" is not built: session transcripts relocate with `CLAUDE_CONFIG_DIR` **[doc]**, so the source JSONL lives inside the *other* developer's lane, and `--resume` in the caller's lane would copy one person's transcript into another person's credential directory — defeating the wipe guarantee and making a data-mixing decision the owner has not made. **The other half, plainly:** `resumeProviderSession.transcriptPath` (`terminal.ts:1025`) and `launchConfig.ompResumeFilePath` (`workspace-session-sleeping-agents.ts:71-77`, reachable on `terminal.create`, `session.tabs.createTerminal` and `worktree.create`) are client-supplied paths on the very RPCs that derive the lane **[code]**. §a's `computeLaneLaunch` containment-checks both against **only** the caller's own lane root and the workspace — which also refuses a path under the shared `~/.claude`, so a pre-S9 session cannot be resumed from inside a lane (§a; the refusal names the shared-lane pane as the place to do it). Residual is the §4 one: a paired grant can read those bytes with a shell anyway.

### (h) Presence integration

Two additive fields on terminal/presence rows: `credentialLane: 'grant' | 'host' | 'remote' | 'wsl' | 'shared-runtime' | 'unknown'` (`'shared-runtime'` is the OpenClaude downgrade of §a consequence 3 — a lane pane observed running a runtime the lane cannot isolate) and `laneState: 'loaded' | 'absent' | 'reauth-required'` (plus `'restart-required'` if the §4 live probe fails). **These are properties of the terminal, not of a participant** — they come from the pane's `laneGrantId` (§a), so a shared-lane terminal never renders as owned by a person and a wiped lane says `absent` rather than looking healthy. Because §a's decoupling pins the lane env to *every* lane pane, `credentialLane: 'grant'` now means what the row claims it means for plain shells too.

**The owner label is the authority label — but it is a join, not a shared key.** `participants` is keyed by connectionId with `pairedDeviceId` as a *field* (`terminal-presence-registry.ts:49`, `:14-16`), `attachments` by subscriptionKey (`:50`) **[code]**; the lane is keyed by `pairedDeviceId`. The row projection matches the terminal's `laneGrantId` against each participant's `pairedDeviceId` and marks that participant as the credential owner. Written once, in the projection, it cannot drift. The account **email** on that row, if Q3 says to show one, is client-asserted (§b); the owner label is not.

**The pane's lane must survive a restart — after rev 8 it *is* the binding, not an attribute of it.** `laneGrantId` lives on the in-memory `RuntimePtyWorktreeRecord` (`orca-runtime.ts:1380-1405`, beside `connectionId` at `:1384`) **[code]** and is persisted on the pane's binding row, which both spawn paths already sync-flush before `pty:spawn` returns — `persistPtyBinding` (`src/main/persistence.ts:6901-6935`, paneKey composed at `:6916`, beside `terminalPtyIncarnationsByPaneKey`) — which has **four** writers, not the two rev 8 named: `ipc/pty.ts:5271`/`:5275` (path A), `:6814`/`:6816` (path B), and two *reattach* writers, `ipc/pty.ts:818` (inside the stable-pane persistence fence, `:812-822`) and `ssh/ssh-relay-session.ts:2557` **[code]**. The reattach writers rewrite an existing row from an owner record, so each must **preserve** the row's lane field rather than re-emit the row without it — a dropped lane on reattach is a silent downgrade to `shared`, and §5 asserts it on both; §3 row 6 additionally carries the lane alongside each `claudeLivePtySessionIds` entry (`persistence.ts:7136-7160`) **[code]** so the live-PTY seed can attribute accounts, and the sleeping-agent record carries it too (§a). Rehydrated onto the record at restore **[inferred — the field is new; the two store shapes it joins are those]**, and the reattach writers above are the ones that can silently drop it. Without it, cold restore, the wake, `terminal.split` and relay-lease recovery (`orca-runtime.ts:17221`) **[code]** all read no lane. A pane restored from an *older* state carries none: it renders `credentialLane: 'unknown'` (never attributed to a person), and a split, a recovery **and a resume** of it fail closed.

### (i) macOS, Windows, WSL

**macOS — a hard refusal, not a degradation.** Per-lane isolation is nearly free: the Keychain service is already suffixed by `sha256(CLAUDE_CONFIG_DIR)` (`keychain.ts:85-93`) **[code]**. What breaks it is the legacy fallback: `getActiveClaudeServices` returns `[scoped, unsuffixed]` and readers/writers walk both (`:95-100`) **[code]**, and `runtime-auth-service.ts:424`'s comment explains why — "Claude Code 2.1+ reads the scoped service, older builds the legacy unsuffixed one" **[code]**. With a pre-2.1 CLI every lane collapses onto the single unsuffixed item: all grants share one credential and **R1/R3 fail silently**. **Decision:** on macOS the lane path never touches the unsuffixed service, and lane provisioning **refuses** below the pinned CLI version rather than degrading. The shared lane keeps the fallback. Wipe must also delete the lane's scoped Keychain item. **The fail-closed claim for a *wiped* lane needs its own probe:** `getActiveClaudeServices` returning `[scoped, unsuffixed]` (`keychain.ts:95-100`) **[code]** is *Orca's reader* behavior, not documented CLI behavior. If the CLI does fall back, a wiped lane silently runs on the shared credential. §5 adds a macOS probe on the pinned version; until it passes, macOS lane provisioning stays off — **a hard gate restated in §6, not a note**. And because a live probe on a real Mac cannot protect the reader from regressing on CI, S9a also ships an **in-repo control with a mutation proof**: a unit test asserts that the lane read/write path resolves the *scoped* service only, and making any lane path reach the unsuffixed service (e.g. restoring the `[scoped, unsuffixed]` walk of `keychain.ts:95-100` **[code]** on the lane branch) must turn a named test red. This failure class — every lane silently collapsing onto one credential — is the worst in the design, so it must fail loudly in CI, not only in a manual step.

**Windows.** `writeFileAtomically(…, { mode: 0o600 })` is effectively a no-op for Windows ACLs **[inferred]**. The lane directory must be created with an explicit ACL granting only the runtime user and removing inherited ACEs before the first credential lands; verify by reading back the DACL, not the mode bits. Note the second-order effect §a already relies on: a failing `hardenExistingSecureFile` is exactly what makes `DeviceRegistry.load` return zero devices (`device-registry.ts:340`, `:363-365`) **[code]**, which is why orphan reconciliation is gated on a successful load.

**WSL.** Lanes do not apply (§a); a WSL-target launch keeps today's per-account WSL config dir, labelled `credentialLane: 'wsl'`, and the WSLENV export invariant in §a is asserted so no host lane path ever crosses into a distro. On a Windows host a grant's WSL panes are therefore **not** isolated from another grant's WSL panes — a stated gap, and the reason the WSL-visible lane is a later slice.

### (j) Launch scrub — unchanged, plus new negative controls

The strip and the refusal stay as they are: the `authEnvToDelete`/`envToDelete` construction gated on `claudeAuth?.stripAuthEnv` (`ipc/pty.ts:4737-4739`, `:6429-6431`) over `CLAUDE_AUTH_ENV_VARS` (`environment.ts:1-6`), with the refusal at `:4592-4596`/`:6176-6180` **[code]** — the lane branch's `stripAuthEnv: true` is what arms them, now on every lane pane (§a). (`applyClaudeEnvPatch`'s strip path, `environment.ts:13-35`, is never invoked from `pty.ts` **[code]**; it serves Orca's two own probes.) These are joined by the `CLAUDE_CONFIG_DIR` and `agentArgs` guards from §a.

Because `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`apiKeyHelper` **outrank** stored logins **[doc]**, a lane is only as strong as the settings files the CLI reads *and the arguments that choose them*. Rev 6 answered "three surfaces" one at a time and missed a fourth (host-wide `agentDefaultArgs`); rev 7 answers them from §2's enumeration instead, and only one row needs an answer §2 cannot give structurally: **row 22**, a project-level `.claude/settings.json`, resolved from the cwd rather than the config dir **[doc]** — and that cwd is a folder workspace as often as a git worktree (`AGENTS.md:43-45`) **[code]**. The host does not own that file, so the answer is a **refusal**: S9a refuses a lane launch when resolved project settings define `apiKeyHelper` or auth `env` keys. Rows 5–14 (client `env`/`envToDelete`/`agentEnv`/`agentArgs`/`agentCommand`, and host-wide `agentDefaultArgs`/`agentDefaultEnv`) are computed away by `computeLaneLaunch`; row 20 (the host's own `settings.json`) is ignored except the §a mirror. Two neighbours are **named rather than refused**: enterprise **managed policy** (`/etc/claude-code/managed-settings.json`) outranks every lane `settings.json` and is not relocated **[doc]** — root-only, so §4 class and invisible to this refusal; and the **base-URL class** env keys (row 5), which redirect only the lane owner's own pane. Controls: a lane launch in a workspace whose `.claude/settings.json` defines `apiKeyHelper` must throw (once for a worktree, once for a folder workspace); a lane whose own `settings.json` is mutated on disk to add `apiKeyHelper` must be rewritten or refused at next launch; a lane launch whose `agentArgs` contains a settings-redirecting flag must be refused, once per spawning RPC; and a lane launch made while a peer's `settings.update` has set `agentDefaultArgs`/`agentDefaultEnv` must carry neither; and a lane launch made while a peer has set `agentStatusHooksEnabled: false` still carries the hook coordinates (row 16).

### (k) Usage and rate-limit attribution

Relocating `CLAUDE_CONFIG_DIR` breaks Claude usage telemetry. The managed statusline posts `configDir=$CLAUDE_CONFIG_DIR` (`claude/statusline-script.ts:160`; Windows branch `:57-58`) **[code]** — and §a requires every lane's `settings.json` to carry that hook block. `rate-limits/service.ts:1465-1468` snapshots **one** host-wide `configDir` from `authPreparation?.envPatch.CLAUDE_CONFIG_DIR` and drops any event whose `configDir` does not match (`:1483-1489`) **[code]**. Rev 8 adds the dependency row 16 now carries: the post exists only if the hook env was injected, and that injection is gated at spawn by `isAgentStatusHooksEnabled(ptySettings)` at three sites — `pty.ts:4724`, `:6405` (daemon) and `:2478` (non-daemon, via `local-pty-provider.ts:723`) → `agentHookServer.buildPtyEnv()` `:1777` **[code]** — a host-wide, ungated, client-writable flag, which is why the lane read is lane-scoped and always on. Without a change, every lane terminal's usage post is silently discarded while §d promises the projection carries "the caller's own lane row".

**S9b makes the snapshot a map.** `lastClaudeAuthSnapshot` becomes `Map<normalizedConfigDir, { provenance, laneId, identity }>`, populated by the shared-lane fetch as today plus one entry per loaded lane from §c's `syncLane`; `ingestLiveClaudeRateLimits` (`:1472-1489`) looks the event's `configDir` up in that map and attributes to the matching lane, still dropping unknown dirs. (2) The *pull* path is not fixed by this: `buildClaudeUsageReadOptions` derives read options from a single `authPreparation.configDir` (`rate-limits/claude-fetcher.ts:238-246`) **[code]**, and the inactive-account preview builds its own preparation per account (`:1076-1082`) **[code]**. ## 3. Wire changes

All gated behind one new runtime capability, `agent.identity-lanes.v1`, declared beside its siblings (`src/shared/protocol-version.ts:77`) and added to `RUNTIME_CAPABILITIES` (`:106-144`) **[code]**; the client check follows `src/cli/handlers/account.ts:276-284`'s `capabilities?.includes(...)` precedent (check at `:278`) **[code]**.

**Rule classification note.** The three rules in `docs/reference/remote-wire-compatibility.md` do not cover new RPC *methods*. Rule 2 is about stream **opcodes**, and its rationale is that an unknown opcode "vanishes, and the feature behind it appears to hang" (`:31-44`) **[code]**. New methods do the opposite: `dispatcher.ts:44-54` and `:139-150` return `method_not_found` loudly **[code]**. So new methods are a **fourth case** the doc does not cover: failure is loud, but the client should still capability-gate so the user sees "update the host". Add that distinction to the wire doc alongside S9.

## 4. Threat model

**What the design fixes.** Remote account hijack of a *lane* via `accounts.selectClaude` and deletion via `removeClaude` (today: any paired client moves or deletes everyone's credential, `accounts.ts:113-117`, `:137-141`) **[code]**; silent cross-switching between the two developers; misattribution of work — and of usage (§2k) — to the wrong account, **including on plain-shell panes, which rev 5 would have mislabelled while running on the other developer's credential (§2a)**; the process-global switch gate stalling the other developer's spawns; the `CLAUDE_CONFIG_DIR` injection in §2a — override *and* deletion, on all three spawning RPCs, and today it reaches the real managed-account store; **cross-grant launch redirection through host-wide settings** — any paired grant can set `agentDefaultArgs`/`agentDefaultEnv` through an identity-ungated `settings.update` (`client-ui.ts:20-25`, `client-ui-schemas.ts:139-146`) **[code]** and shape another grant's Claude invocation, which §2's closure principle removes by computing lane launches instead of customizing them; the `--config-dir` capture path in §2d, symlinks included; the unscoped account-snapshot disclosure in `list`/`subscribe`; **the two client-reachable spawn edges rev 7's anchor missed** — a lane holder's own `focus`/`rendererBacked` create landing silently in the shared `~/.claude` through `pty:spawn`, and a peer's `worktree.activate` re-launching another grant's sleeping lane agents from host-wide settings (§2a) — and **a peer switching off `agentStatusHooksEnabled` to strip the hook coordinates from another grant's lane spawn env**, which would have ended that lane's usage attribution (row 16). **Rev 9 adds three that rev 8's anchor did not reach:** a lane holder's `session.tabs.createTerminal` landing in the shared `~/.claude` whenever a desktop window exists, because that RPC's branch key is window presence rather than a client flag (`orca-runtime.ts:27060-27062`, row 29); the same `agentStatusHooksEnabled` strip surviving on the **non-daemon** provider, where the read is `pty.ts:2478` inside `buildSpawnEnv` and no lane could reach it (rows 16, 30); and a client-hinted `tabId`/`leafId` adopting — or, on a dead PTY, respawning into — a pane bound to another grant's lane (`:26393-26400` before `:26419`, §2a(ii)).

**And one authority hole that is not a confidentiality concession.** Without §2a's ownership predicate, `orchestration.workerStart` (`orchestration-workers.ts:29`, pane from `params.from` at `:31`) **[code]** — on **both** its topology paths — and `terminal.split` (`terminal.ts:1565`) **[code]** would let grant B *spend* grant A's Claude account through Orca's own supported RPCs. That is categorically different from the concession below: not "B can read bytes B could read anyway", but Orca granting B the use of A's subscription.

**What it does not fix, and this is the load-bearing concession.** A paired grant is **shell-equivalent** on this host. `terminal.create` has no `clientKind` gate and its params include `command` (`terminal.ts:1005`), `env` (`:1007`) and `launchConfig.agentCommand`/`agentArgs`/`agentEnv` (`:1011-1013`), all passed straight through (`:1537-1541`) **[code]**; `terminal.split` likewise (`:1051-1052`, `:1568-1569`) **[code]**. Orca's own authorization precedent says this outright: the runtime-scope pairing "lets it create terminals and drive agents on this host (`terminal.send`, `worker-start`), so it could always post and read Run mail by driving a local pane" (`orchestration-remote-run-mailbox.ts:11-22`, esp. `:16-18`) **[code]**. Grant B can therefore call `terminal.create` with `command: cat <userData>/claude-grants/<A>/.credentials.json` and read the output over a stream it is authorized to read. **So: lanes defend against accidental cross-switching and the `selectClaude`-class hijack; they do not defend against a hostile paired grant.**

Same for the local surface: both developers run as the **same Unix user**. `0600` protects nothing from a peer who *is* that user — `cat` the lane file while it is resident, read `/proc/<pid>/environ` for the lane path, or `ptrace` a running `claude`. Root adds wiped-but-not-shredded blocks. A hostile project `.claude/settings.json` can redirect auth for any lane launched there (§2j) — a refusal, not containment. **Residuals accepted and named:** **OpenClaude cannot be lane-isolated today** — no `CLAUDE_CONFIG_DIR` mapping exists for `~/.openclaude` in this tree, so lane launches of it are refused and a hand-typed session downgrades its row (§2a, unverified **[inferred]** until the §5 probe); enterprise **managed policy** outranks a lane's own settings and is invisible to §2j's refusal (root-only); the **base-URL** env class lets a lane owner redirect their own pane's CLI traffic (row 5, self-directed); **R-DR2**, a second Orca install holding the same account rotates it out from under the lane and only detection ships (§2e); Codex selection stays host-wide and unscoped (`accounts.ts:118-130`) **[code]**; a grant with **no** lane can still move the shared lane under other lane-less peers, for accounts not resident in a lane (§2d — Q5); WSL panes isolate per account, not per grant (§2i); lane usage is statusline-only until the per-lane pull ships (§2k — Q7); a lane forks Claude's session history and resume surface (§2a — Q9); an anonymous local caller can inherit any pane's lane (§2a case (ii)); and the wipe has a residency window bounded by close detection, idle timeout and the startup wipe (§2f). The only real confidentiality fix is two Unix users, which the owner has ruled out.

If the owner wants R1 to hold against a hostile grant, the achievable control is **lane-strict mode** (Q6). §2's closure principle already removes the *customization* half — `env`, `agentEnv`, `agentCommand`/`agentArgs` and resume paths are computed or allowlisted for a lane launch — so what lane-strict adds is the rest: once the caller holds a lane, its sockets may not supply a free-form `command` at all, only named launch configs the host already knows. A large functional cut, so the default is **off**.

**Version pin, and what happens if it fails.** The design rests on one behavior — the running CLI re-reads relocated credentials — and credential resolution has changed across releases (the v2.1.225 note) **[doc]**; Orca already pins its OAuth constants against a specific binary ("verified against the installed `claude` binary (2.1.177)", `claude-accounts/oauth-refresh.ts:4-8`) **[code]**. Record the tested range here, probe `claude --version` at lane provisioning, and refuse outside it — on macOS unconditionally (§2i). **If the §5 live probe fails on the pinned version, S9 does not die; R2 degrades.** Lanes still isolate: R1, R3 and R4 hold, because isolation depends on the *launch-time* `CLAUDE_CONFIG_DIR`, not on re-reads. What is lost is live switching — a push then takes effect for **new** terminals in that lane only, `laneState` gains `'restart-required'`, and the AccountsPane hedge (`AccountsPane.tsx:808`) **[code]** becomes the accurate UI instead of a hedge.

## 7. Open questions for the owner

1. **Cross-grant delegation for one human.** May the owner's *phone* or second desktop (separate grants) push to / switch the owner's primary lane? Convenient, and exactly the hole R1 closes. Default if unanswered: no — one grant, one lane. Note two consequences either way: two of your own grants cannot hold the same account simultaneously (L1), and a second Orca *install* holding that account will revoke it out from under the lane (R-DR2, §2e) — do you want the UI to hard-refuse provisioning until you confirm the account is logged out elsewhere?
2. **Rotated-token return path.** The host rotates and also observes CLI rotations (§2c/§2e). Pull the rotated blob back to the desktop on every receipt (one more secret transfer), or let the lane be authoritative until the next `claude login` (desktop store goes stale)?
3. **Identity label the *other* developer sees** on a presence row and in the projected `accounts.list`: account email, a friendly per-account name, or grant label only? Email is the most useful and the least private — and note it is **client-asserted** (§2b): the pushing desktop chooses the string. The grant/owner label is host-observed and cannot be faked.
4. **Handoff scope-out.** Confirm transcript-seeded "continue in my account" stays out of S9 (§2g), given the recipient can already read the screen and (§4) drive a shell.
5. **Shared-lane switching.** With refusals caller-scoped (§2d), a grant that holds no lane can still move the shared lane host-wide. Lock the shared lane to anonymous local callers once *any* lane exists, or leave it open?
6. **Lane-strict mode (§4).** Ship the option that refuses client-supplied `command`, `env`, `agentEnv`, `launchConfig.agentCommand`/`agentArgs` and client-side resume paths from a lane-holding socket — default off, owner opt-in? Without it, a paired grant can read any resident lane file, and R1 is an authority guarantee only. This is the one question that changes what R1 means.
7. **Lane usage bars (§2k).** Statusline-only attribution ships in S9b; the per-lane usage *pull* is a later slice. Acceptable that a lane account shows no usage until its first statusline post, or should the pull come forward into S9b?
8. **Cross-grant orchestration.** §2a's ownership predicate means the other developer can no longer call `orchestration.workerStart` against *your* coordinator pane, or split your terminal, from their own client — they must type it into your pane instead (which still works, and still spends your account, visibly). Confirm the cut, or ask for an explicit per-pane "let this grant spend my lane" opt-in as a later slice.
9. **Lane session forking (§2a, reversing `global-settings-types.ts:253`).** A lane relocates `.claude.json`, transcripts and memory as a unit, so inside a lane `--resume` sees only that lane's sessions and pre-S9 sessions are unreachable. The design mirrors user-level **memory**, the **permission allowlists** and **MCP server entries** into each lane, and mirrors **no** transcripts, **no** user hooks, **no** trust map and **no** plugin state (§2a, item by item). Confirm: is the memory mirror wanted (it duplicates a file both developers currently share); is per-grant session history intended rather than a regression to work around; and is the new mirror of user-level `agents/`, `commands/`, `skills/` and `output-styles/` wanted on the same terms as memory (it duplicates files both developers share today, and a lane's own additions do not flow back); and are the two remaining re-prompts acceptable — one trust prompt per lane per workspace, and no plugins in a lane until a later slice mirrors them?
10. **OpenClaude in a lane (§2a, MAJOR 3 of round 7).** Nothing in this tree maps `CLAUDE_CONFIG_DIR` onto `~/.openclaude`, so the design **refuses** lane launches of OpenClaude and downgrades a hand-typed one's row rather than claiming an isolation it cannot evidence. Confirm the refusal — or, if you would rather keep OpenClaude usable inside a lane, confirm the alternative: the pane is marked `credentialLane: 'shared'`, rendered as shared, and its usage is never attributed to the lane owner. The §5 live probe can retire the question entirely if the binary turns out to honor the variable.
